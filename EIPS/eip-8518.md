## Abstract

This EIP defines `eth/76`, extending [EIP-8512](./eip-8512.md) with aggregate proof wrappers, coverage hints, transaction-hash manifests and compact retrieval. Individual transactions continue to propagate with segregated witnesses in [EIP-8141](./eip-8141.md)'s pooled form.

## Motivation

Relaying reusable aggregates can replace many individual witnesses with one proof and reduce the proving work left to builders during block construction. Aggregators can produce overlapping proofs for the same transactions. Wrapper hashes alone do not identify equivalent coverage when proof bytes differ, and repeatedly transmitting transaction encodings wastes bandwidth. Aggregate propagation needs coverage-aware discovery and retrieval.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

`eth/76` extends `eth/74` and uses its message semantics except as specified below. Status (`0x00`) is unchanged; the protocol version and new message IDs are provisional. Request IDs follow [EIP-2481](./eip-2481.md). The *mempool fork* is selected by configured activation timestamps at the client's current Unix time in seconds, independently of its head block.

In the Recursive Length Prefix (RLP) encodings below, `P` is a nonnegative integer (zero encodes as the empty byte string), `B` is a byte string, and `B_n` is a byte string of exactly `n` bytes.

### Wrapper encoding

The canonical wrapper carries an [EIP-8288](./eip-8288.md) aggregate as `[transactions, deps, recursive-stark]`:

- `transactions`: a nonempty list of the aggregate transaction encodings below, as byte strings in strictly ascending consensus transaction-hash order.
- `deps`: the sorted, deduplicated union of the transactions' aggregatable claims, mapped to EIP-8288's strictly byte-lexicographically ordered 96-byte dependencies.
- `recursive-stark`: one nonempty EIP-8288 proof of `deps` under the mempool fork's verifier.

The activating fork MUST define which EIP-8141 protocol verifiers are aggregatable and their mapping to EIP-8288 dependencies. The mapping MUST unambiguously preserve the resolved verifier, key and message; custom contract claims MUST NOT be treated as aggregatable without an explicit core rule. Each enclosed transaction MUST have at least one aggregatable claim. This transport does not enable additional verifiers.

An aggregate transaction uses EIP-8141's pooled encoding, `FRAME_TX_TYPE || rlp([tx_body, wrapper_version, witnesses, blob_sidecar])`. The witness list retains one position per declared claim, including repetitions: each aggregatable claim's witness MUST be the empty byte string; all other claims retain their complete witnesses. Only the aggregate proof substitutes for the omitted witnesses. Claim resolution, consensus hashes and validation of retained witnesses follow EIP-8141. Blob data is elided under [EIP-8070](./eip-8070.md); commitments and cell proofs remain.

The complete canonical RLP encoding MUST be at most `MAX_WRAPPER_BYTES = 2**21` (2 MiB); EIP-8288's applicable dependency limits also apply. Wrapper identity is Keccak-256 of this complete encoding. Hash references are transport-only and MUST be resolved before applying the byte bound or computing the hash. An aggregate transaction with omitted witnesses MUST NOT be served as a complete pooled transaction.

### New messages

Messages use canonical RLP with the structures below and no extra fields or trailing bytes. Until the mempool fork enables aggregation and the claim mapping above, clients MUST NOT send wrapper messages and MUST ignore received ones without penalties; underlying transport size limits still apply.

#### NewProofWrapperHashes (0x18)

`[[length₀: P, hash₀: B_32, deps-hash₀: B_32, txs-hash₀: B_32], ...]`

Announce 1–64 held, validated wrappers in strictly ascending hash order, with canonical length 1–`MAX_WRAPPER_BYTES`. Peers SHOULD announce newly validated wrappers to every connected `eth/76` peer, subject to suppression below, and on connection up to 64 offered wrappers covering pending transactions, most recent first.

The complete announcement payload MUST NOT exceed 6,723 bytes. Receivers MUST check this bound before decoding.

- `deps-hash`: Keccak-256 of the concatenated 96-byte entries in `deps`.
- `txs-hash`: Keccak-256 of the concatenated, ascending consensus transaction hashes.

Under the same verification rules, peers SHOULD suppress hashes already exchanged on the connection; they MAY re-announce after a local interval or eviction from the connection's bounded record. Requesters MAY skip a fetch when both digests match a held, validated wrapper. Hints alone establish no coverage or validity; matching only `deps-hash` does not identify the transactions.

Peers SHOULD announce a wrapper only if it adds aggregate coverage or reduces proof bytes or locally estimated verification work for the recipient. Compare against held, validated aggregates whose hashes either peer has announced on the connection or whose bodies have been exchanged, under the same verification rules. Knowing a transaction or its raw witness does not establish aggregate coverage. Verification-work estimates use local verification-only measurements, not gas charges.

#### GetProofWrappers (0x19)

`[request-id: P, compact: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request 1–32 distinct wrapper hashes previously announced by the responder on this connection under the same verification rules. Responders MUST treat other hashes as unavailable without penalizing the request, since announcement records may be bounded. `compact` is `0` or `1`: with `0`, returned wrappers MUST contain complete transaction encodings; with `1`, responders MAY use [hash-based omission](#hash-based-omission).

#### ProofWrappers (0x1a)

`[request-id: P, [[hash₀: B_32, wrapper₀], [hash₁: B_32, wrapper₁], ...]]`

Return available validated wrappers as embedded RLP items in the [wrapper encoding](#wrapper-encoding), paired with their canonical hashes, in request order with omissions allowed and no repeats. The recommended soft response limit is 2 MiB. Responders SHOULD stop after reaching it, returning complete wrappers only. Empty responses are permitted.

Requesters MUST match distinct requested hashes in order and check canonical hashes and full lengths against the responder's announcements. They re-request hashes after the last returned wrapper; earlier omissions are unavailable from that peer. Requesters SHOULD fetch each wrapper from one announcer at a time and try another after an empty response or timeout.

Responders whose serving budget is spent SHOULD return an empty response rather than omit wrappers or stay silent. Requesters SHOULD NOT penalize an empty response or count it toward a limit on sources tried for a wrapper. They MAY score earlier omissions in a nonempty response in proportion to the requested wrappers withheld, and SHOULD count an unanswered request against the peer.

#### GetProofWrapperManifests (0x1b)

`[request-id: P, [hash₀: B_32, hash₁: B_32, ...]]`

Request the manifests of 1 to 32 distinct wrappers, each previously announced by the responder on that connection under the same verification rules; responders treat other hashes as GetProofWrappers does. A wrapper's manifest is the strictly ascending list of all its consensus transaction hashes, regardless of transaction count. Requesters SHOULD fetch a manifest only when comparing its hashes with held coverage may avoid a wrapper fetch; otherwise they SHOULD request the wrapper directly.

#### ProofWrapperManifests (0x1c)

`[request-id: P, [[hash₀: B_32, [txhash₀: B_32, ...]], ...]]`

Return the manifests of available validated wrappers, paired with their hashes. ProofWrappers' response matching, omission and retry rules, soft response limit, empty responses and scoring apply, with complete manifests in place of wrappers, and served manifests count toward the serving budget. Responders SHOULD keep each validated wrapper's manifest rather than derive it per request. Requesters MUST check a manifest on arrival as specified under [Validation](#validation), and against the wrapper if they fetch it.

### Hash-based omission

Compact responses reconstruct the same canonical wrapper using locally cached transaction encodings.

- With `compact = 1`, responders MAY replace transaction bytes with `[encoding-hash: B_32]`, if smaller. They SHOULD do so when prior wrapper exchanges or announcements indicate the requester holds the encoding. The hash is Keccak-256 of the aggregate transaction bytes, excluding the enclosing Recursive Length Prefix (RLP) string prefix. References are RLP lists; transactions are byte strings.
- A validated pooled transaction can supply a cache entry by emptying its aggregatable witness positions and eliding blob data. The other witnesses and sidecar metadata MUST be preserved. Requesters MUST resolve references by encoding hash from any locally cached, validated aggregate transaction encoding, regardless of which peer supplied it, and check their hashes. The complete wrapper determines identity and byte limits; reconstruction MUST stay within the announced length.
- On a missing encoding, requesters MUST discard the compact item and SHOULD retry with `compact = 0` and a fresh request ID. Cache misses MUST NOT incur penalties.

### Transaction and blob propagation

EIP-8141's announce-and-fetch propagation remains available on every connection: NewPooledTransactionHashes (`0x08`), GetPooledTransactions (`0x09`) and PooledTransactions (`0x0a`) exchange complete pooled transactions. Frame transactions MUST NOT appear in Transactions (`0x02`), as specified by EIP-8141. Aggregate coverage does not make an incomplete pooled form serveable. Builder aggregation alone requires no wrapper messages.

[GetCells/Cells](./eip-8408.md) use consensus transaction hashes. Clients MUST validate the aggregate and retained witnesses before cell retrieval and complete EIP-8070's availability checks before pool admission. Wrapper announcements do not count as cell providers; valid wrappers may circulate before availability is established. Cell announcements and sampling follow EIP-8070.

### Peers without aggregate transport

Clients MUST send wrapper messages only on `eth/76` connections. While connected to peers using only pooled propagation, clients SHOULD fetch and retain complete witnesses for pending transactions and announce their pooled forms, even when aggregates cover those transactions. Aggregate coverage MUST NOT by itself suppress a fetch needed to serve such a peer. Fetching and retention remain subject to local budgets and current verification rules. Clients MAY release data retained solely for such peers when none remain connected.

An aggregate cannot reconstruct omitted witnesses. A transaction for which no complete witnesses remain is available only through aggregate transport. A wrapper discarded as unsupported on one connection is not thereby invalid; that discard MUST NOT suppress fetching the same hash from a compatible peer.

### Validation

Clients MUST check transport and hints before proof verification, verify the aggregate against the exact mapped dependency union, and validate all retained witnesses under EIP-8141 before announcement, serving, reaggregation or transaction admission. Decoders MUST accept structurally valid dependencies with unknown scheme identifiers; active core rules determine validity.

- Received data MUST remain in bounded request-scoped storage until validation completes and be discarded on cancellation or timeout. Before decoding or hashing bodies or manifests, requesters SHOULD check that the request is outstanding and its connection open.
- When the mempool fork's verification rules change, wrappers validated only under the previous rules MUST NOT be served, announced or used to suppress announcements.
- Transport item-count, hard byte-length and response-order violations SHOULD cause disconnection. Malformed encodings, unmatched responses, hash or length mismatches, and references in a `compact = 0` response MUST be discarded and MAY cause penalties or disconnection. Crossing the soft response limit alone MUST NOT cause penalties.
- A manifest MUST be a nonempty, strictly ascending list of 32-byte hashes whose RLP encoding is smaller than the announced wrapper. Its concatenated hashes MUST hash to the sender's `txs-hash` on arrival.
- Before proof verification, clients MUST check the serving peer's announcement digests and any manifest against the reconstructed wrapper. A mismatch MUST cause discard and SHOULD cause disconnection of that peer, independently of proof validity. Hints and manifests are kept per peer; unverified claims MUST NOT suppress another peer's offer or establish validated coverage.
- Pool rejection of an individual transaction does not invalidate its covering wrapper and MUST NOT incur peer penalties. Clients SHOULD relay such a wrapper unchanged only if it newly admitted at least one transaction and no fewer than it rejected; already-pending transactions count as neither.
- Proof, retained-witness or dependency-rule failures MUST cause discard. Clients MAY deprioritize or rate-limit further fetches, but MUST NOT penalize or disconnect a peer solely for these failures, even when repeated.
- Clients MAY deprioritize, rate-limit or disconnect peers that repeatedly fail to answer requests. Fetch limits SHOULD be retained by node identity across reconnections. Responders SHOULD skip requests from closed connections and bound served bytes globally and fairly between peers.

## Rationale

Individual signatures have no shared proof to amortize. EIP-8141's pooled form already carries the transaction with the witnesses needed to validate it. Wrappers serve the separate purpose of reusing one proof across transactions; they need neither a mode field nor direct-witness metadata. They carry complete transaction bodies and any uncovered witnesses so receivers can validate without awaiting another object.

Dependency and transaction digests identify equivalent coverage despite different proof bytes. `txs-hash` distinguishes transactions sharing dependencies. The wire dependency digest uses a fixed hash of encoded triples rather than the circuit digest, allowing checks independent of fork verification rules.

Hashes-only manifests identify partial overlap; fee-based ranking uses transactions already held. Requesting the wrapper directly avoids a round trip when overlap would not affect the decision. Compact responses reuse encodings from any peer, including normalized pooled transactions. Encoding hashes bind retained witnesses and blob metadata as well as transaction bodies; a consensus hash alone would not. A full retry handles cache misses without another request protocol.

## Backwards Compatibility

Complete witnessed transactions remain available through EIP-8141's pooled propagation, including to peers without `eth/76`. Aggregate transport requires the core fork's claim mapping and proof verifier; negotiating the version does not activate either. Consensus transaction hashes, signing and block-proof exchange are unaffected.

## Test Cases

[Announcement vectors](../assets/eip-8518/announcement-vectors.json), [wrapper vectors](../assets/eip-8518/wrapper-vectors.json) and [the checker](../assets/eip-8518/check_vectors.py) cover encoding and matching. Synthetic verifier addresses, witnesses and proofs do not test core validity or cryptography.

| Case | Expected result |
| --- | --- |
| Maximum announcement/request; excess counts or unordered hashes | Accept bounds; reject excess and malformed order |
| Raw pooled transaction normalized for aggregate transport | Preserve consensus hash; empty covered witness slots only |
| Repeated claims and a nonaggregatable claim | Preserve all witness positions; deduplicate only the aggregate dependencies |
| Wrong witness count, retained covered witness or missing uncovered witness | Reject |
| Different raw signatures for the same claim | Same aggregate encoding after normalization |
| Changed retained witness or blob metadata | Different encoding hash, even with an equal consensus hash |
| Full and compact responses; references cached from pooled propagation | Reconstruct the same canonical wrapper |
| Missing reference, reference in a full response, wrong cache entry or excessive reconstruction | Retry in full on a miss; reject malformed responses |
| False digest or manifest, even with an invalid proof | Reject before proof verification; attribute the mismatch to its sender |
| Repeated, reordered, omitted or unannounced responses | Reject unmatched entries; permit omissions and empty responses |
| Equivalent coverage, different proof bytes | Equal hints allow skipping a fetch using held validated coverage |

Client integration cases:

- Retain complete pooled witnesses while serving a peer without aggregate transport, including when an aggregate already covers the transaction. Fetching the aggregate cannot recover dropped signatures.
- Receive a pooled transaction and its first covering aggregate: raw-witness possession does not suppress aggregate discovery.
- Validate an aggregate covering a transaction with an additional custom-verifier claim. Run the retained witness check; reject if it fails even when the aggregate is valid.
- Before aggregation activation, use pooled propagation and ignore wrapper messages. After a verifier change, revalidate cached wrappers before serving or suppressing offers.
- One peer's misleading manifest or an unsupported connection must not suppress fetching the same wrapper from another compatible peer.
- Apply ordinary per-transaction pool admission and blob availability checks after validating coverage; an individually rejected transaction does not invalidate the proof.

## Security Considerations

Clients should bound announcements, requests, buffered and cached bytes, serving traffic and verification work per peer and globally across node identities. Aggregate budgets should account for recursive verification and any retained witnesses, including expensive custom-verifier claims. Manifest processing and reconstruction need byte and record limits. Exhaustion permits refusal without making a wrapper invalid.

Hints remain claims until checked against validated contents. Cheap checks and fetch limits should precede verification. Request deadlines limit withholding. Validation before relay adds latency at each hop; propagation within the aggregation interval requires measurement. EIP-8070's blobpool safeguards apply. Retaining raw witnesses for peers without aggregate transport consumes additional, locally bounded storage.
