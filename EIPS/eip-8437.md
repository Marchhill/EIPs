## Abstract

This EIP defines requested retrieval of [EIP-8288](./eip-8288.md) mempool wrappers over `lean/1` devp2p or ethp2p. An experimental ethp2p extension adds authenticated block-proof broadcast and requested recovery. Only authenticated shards may be forwarded before full validation; admission always requires it. Transaction envelopes use ETH retrieval.

## Motivation

Dependency witnesses and aggregated proofs can be much larger than ordinary transactions. Whole-object messages occupy the connection while being written and make interrupted retrieval expensive. Unsolicited objects also consume receiver resources before the receiver decides whether it needs them.

Requested chunks bound each transfer and let proof traffic interleave with other messages. Hash-only wrappers keep object identity independent of which transactions each peer already holds.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Constants

EIP-8288 defines wrapper encoding, validity and proof limits. Block-proof descriptors and messages `0x06`/`0x07` are enabled only under broadcast ALPN `ethp2p_lean_bcast_1`. RLPx and retrieval ALPN `ethp2p_lean_1` transfer only wrappers and MUST NOT send those two message IDs.

The network's deployment configuration MUST designate a common binding, RLPx or the ethp2p profile below, which all participating nodes MUST support. Additional bindings are optional. A migration MUST preserve a common binding until the coordinated transition. A node unable to run it MUST fail to start or disable this protocol and report nonparticipation; silently using other bindings alone is not permitted. Ethp2p-only deployment also requires a network-specified, interoperable binding for ETH envelope-retrieval semantics; this EIP adds no transaction-retrieval messages.

| Name | Value | Meaning |

| `CAPABILITY` | `lean/1` | Capability name and version |
| `MESSAGE_COUNT` | `6` | Core message IDs `0x00` through `0x05` |
| `CHUNK_BYTES` | `65536` | Fixed object chunk size |
| `MAX_OBJECT_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | 9 MiB transport ceiling |
| `MAX_MESSAGE_BYTES` | `131072` | Uncompressed message-data ceiling |
| `MAX_RLP_DEPTH` | `8` | Maximum nesting of transport lists |
| `MAX_PROFILES` | `16` | Profile IDs in Status |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per announcement |
| `MAX_LOOKUPS` | `16` | Selectors per GetBlockProofs request |
| `MAX_CHUNKS_PER_REQUEST` | `32` | Chunk indices per request |

| `MAX_BUFFERED_BYTES_PER_PEER` | `2 * MAX_OBJECT_BYTES` | Unvalidated bytes charged to one source |

| `MAX_BROADCAST_SESSIONS` | `4` | Live ethp2p block-proof sessions per node |
| `MAX_SHARD_DEFERRAL_SECONDS` | `1` | Deferral for an unknown broadcast manifest |

These are transport ceilings, not consensus validity limits. A client MAY enforce lower local limits and refuse work without penalizing the peer. A transport refusal MUST NOT be treated as an invalid transaction or block. Request limits do not reserve an entire object per request; all requests share the byte budgets above.

### Local Resource Policy

Clients MUST configure finite request and assembly idle and absolute lifetimes, and a finite source-attempt budget. RECOMMENDED defaults are request idle/absolute lifetimes of 30/120 seconds, assembly idle/absolute lifetimes of 30/300 seconds, and three source attempts. These are local policy, not negotiated wire limits. The chosen limits apply for each request or assembly's lifetime; retries and source changes MUST NOT renew them. Different local limits are not peer misbehavior.

### Encoding

Message data and object bodies use canonical RLP with exactly the field counts specified. Integers use the shortest unsigned encoding, with zero as the empty string; stated widths are range bounds, not fixed-width fields. Leading zeros, extra fields, trailing bytes, nonminimal length prefixes and wrong list/string types are invalid. Hashes are exactly 32 bytes. Byte strings sort lexicographically. Lists MUST be checked against their count bounds before allocating elements; the outermost RLP list has depth one and nested transport lists MUST NOT exceed `MAX_RLP_DEPTH`. Transaction envelopes and proofs are opaque byte strings at this layer, parsed afterward by their own bounded parsers.

`H` is Keccak-256, not SHA3-256. `RLP(x)` is canonical RLP. In framing, `U8`, `U32` and `U64` are fixed-width big-endian unsigned integers. In commitment formulas, `||` is byte concatenation and a domain label is its ASCII bytes followed by one zero byte.

For the RLPx binding, [RLPx](https://github.com/ethereum/devp2p/blob/76cf0a141e8aa8616e3305738d51101945387d3c/rlpx.md) compression, encryption, message-ID multiplexing and authentication are unchanged. Implementations MUST check the advertised uncompressed size before decompression and reject messages exceeding `MAX_MESSAGE_BYTES`. Requested-retrieval body bytes travel only in Chunk messages, one chunk per message. Implementations MUST NOT rely on RLPx frame fragmentation to carry an object.

### Capability and Profiles

For RLPx, peers negotiate capability name `lean`, version `1`, through Hello; ethp2p uses the application profile below. Both bindings MUST send Status without waiting for the peer's Status. A peer MUST NOT send any other retrieval message before accepting the peer's Status.

A **profile ID** identifies the verification key for an object's recursive STARK:

```text
profile_id = H("lean/1/profile\0" || AGGREGATED_VK)
```

`AGGREGATED_VK` uses the canonical byte encoding fixed by the activated EIP-8288 fork, never a client-specific key serialization. It fixes the cryptographic profile, including dependency hashing and encodings, verifier parameters and bounds, and the circuit's `enabled_schemes` and verification relations. Changing that scheme set requires a new key and therefore a new `profile_id`. Clients derive profile IDs from local fork configuration, never peer-supplied keys. A **common profile** appears in both Status messages and is supported locally.

The receiver MUST check the profile against the local target block's fork for wrappers, or the known block header's fork for block proofs. Forks sharing a key share the cryptographic profile and enabled schemes but may have different transaction or admission rules outside the circuit. Status MAY list known past and future profiles; activation does not update Status, and peers reconnect if new profiles must be advertised. A profile inappropriate for the receiver's target context is not by itself peer misbehavior.

Status is sent exactly once in each direction:

```text
Status (0x00) = [1, chain_id, genesis_hash, profiles, max_object_bytes]
```

- The first field is the Status version, `1`.
- `chain_id` is an unsigned integer less than `2**256`.
- `genesis_hash` is 32 bytes.
- `profiles` is a nonempty, strictly ascending list of at most `MAX_PROFILES` 32-byte profile IDs.
- `max_object_bytes` is an integer in `[1, MAX_OBJECT_BYTES]`: a local receive ceiling, not a promise to accept every smaller object.

The chain ID and genesis hash MUST match local configuration, and at least one profile MUST be common. An incompatible Status disables this capability; clients SHOULD keep other protocols on the connection. Malformed or repeated Status, or other messages received before Status, are protocol violations.

### Wrapper Encoding

An **object** consists of a descriptor and a body of 1 to `MAX_OBJECT_BYTES` bytes. For wrappers, the body MUST be a valid EIP-8288 wrapper in its canonical hash-only encoding.

After checking body integrity and encoding, receivers SHOULD verify the claimed dependency proof before recovering missing envelopes. Every transaction hash still needs resolution and full EIP-8288 wrapper validation before admission, reaggregation or relay. A preliminary proof check does not authenticate the transaction-hash list. Failed recovery leaves the object incomplete rather than invalid.

Envelope recovery uses the negotiated ETH `GetPooledTransactions`/`PooledTransactions` messages. A node offering a wrapper MUST serve its retained envelopes through that interface even when they are absent from its admitted transaction pool. Requests and retention remain bounded; they do not trigger historical searches or recursive peer fetches. Receivers extract the canonical [EIP-2718](./eip-2718.md) envelope from the ETH representation and check its hash. Peers MUST support the network's compatible ETH envelope-retrieval binding to exchange wrappers; it is not provided by the lean QUIC stream profile.

### Block-Proof Encoding

```text
body = RLP([stark_proof])
```

The receiver MUST obtain the ordinary block header before requesting chunks, check the profile against its fork, and after retrieval check `H(stark_proof)` against the header's `stark_proof_hash`. The one-element list keeps the transport body nonempty for an empty proof. Full validation also requires the block transactions and all EIP-8288 block-proof checks; the proof alone does not establish block validity or canonical-chain membership.

A receiver that already has the header and transactions can use this optional path to recover only the proof, including after an incomplete proof broadcast. The proof remains in the block body and execution payload; this path does not omit it from ordinary body responses or reduce their bandwidth. Ordinary block acquisition already supplying those bytes MUST NOT trigger a second required transfer.

### Descriptors and Identity

```text
wrapper_descriptor = [profile_id, byte_length, content_hash]
block_descriptor = [profile_id, block_hash, byte_length, content_hash]
content_hash = H(body)
wrapper_object_id = H("lean/1/object\0" || RLP(wrapper_descriptor))
block_object_id = H("lean/1/block\0" || RLP(block_descriptor))
```

A `descriptor` is a wrapper descriptor (three fields) or, under the broadcast ALPN, a block-proof descriptor (four fields); `object_id` uses the corresponding formula above. `block_hash` is 32 bytes. `byte_length` is a 64-bit unsigned integer within the object bounds. Receivers MUST check its encoding, profile and size before requesting chunks. The same wrapper body produces the same identity for every peer; different proof bytes still identify different objects.

An **assembly** is a receiver's partial copy of an object, keyed by `object_id`; requests are keyed by `(connection, request_id)`. A repeated descriptor MUST NOT create another assembly. A receiver uses one source peer at a time for an assembly, without mixing unverified body bytes from different peers.

### Chunk Geometry

```text
N = ceil(byte_length / CHUNK_BYTES)
chunk[i] = body[i * CHUNK_BYTES : min((i + 1) * CHUNK_BYTES, byte_length)]
```

Thus `1 <= N <= 144`. Every chunk except the last is exactly `CHUNK_BYTES`; the last is `byte_length - (N - 1) * CHUNK_BYTES` bytes. Chunk bytes remain untrusted until the complete body matches `content_hash`. A source switch discards all partial body bytes, while a retry from the same source may request only missing indices.

### Messages and Request Lifecycle

RLPx IDs are relative to the capability's negotiated message offset; ethp2p uses them directly:

| ID | Message | Direction |
| --- | --- | --- |
| `0x00` | Status | Both |
| `0x01` | AnnounceObjects | Both |
| `0x02` | GetChunks | Request |
| `0x03` | Chunk | Response |
| `0x04` | Complete | Terminal GetChunks response |
| `0x05` | Cancel | Requester to responder |
| `0x06` | GetBlockProofs | Request (broadcast ALPN only) |
| `0x07` | BlockProofs | Response (broadcast ALPN only) |

Request IDs are 64-bit unsigned integers. On each connection a peer MUST assign positive, strictly increasing IDs to requests of both types in send order, never wrapping or reusing an ID. Gaps are allowed; each direction has its own sequence, and responses echo the request's ID. A new incoming ID no greater than the preceding one is a protocol violation, even if the request is refused. Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` locally live requests per direction. Responders return Busy for requests they cannot accept. Receiving a request while at the local limit MUST NOT by itself incur a penalty, since expiry times can differ.

Each endpoint measures deadlines with its own monotonic clock: the requester starts when sending the request, the responder when receiving it. Request idle time resets only when receiving a valid first response for a requested result, or when writing that result on the responder. A chunk already obtained through another request to the same source can advance a request without advancing the assembly. Each endpoint retires the request at its idle or absolute deadline, whichever comes first; no synchronized expiry is assumed. Disconnection releases request state. Neither requests nor cancellation reset an assembly's absolute age.

#### AnnounceObjects (0x01)

```text
[descriptor, ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `object_id` order. A sender MUST announce only objects it holds in full and has fully validated under EIP-8288, including the block itself for block proofs. Announced objects MUST use a common profile and fit the receiver's advertised ceiling. Receivers MAY ignore other descriptors without allocating assemblies.

Announcements neither require receiver action nor establish validity. Repetition earns no credit or retention. Peers SHOULD suppress unchanged announcements and rotate bounded selections fairly across useful objects. A receiver that wants an announced object but is at its request or assembly limits SHOULD keep it pending in a bounded cache and retrieve it when capacity frees, since the announcement may not be repeated.

#### GetChunks (0x02), Chunk (0x03), and Complete (0x04)

```text
GetChunks = [request_id, object_id, indices]
Chunk = [request_id, object_id, index, chunk_bytes]
Complete = [request_id, object_id, status]
```

The requester MUST already hold a well-formed descriptor obtained through announcement, block-proof lookup or an authenticated broadcast manifest. It MUST use a common profile and fit the receive ceiling. `indices` is a strictly ascending list of 1 to `MAX_CHUNKS_PER_REQUEST` 32-bit integers less than `N`. The request grants **credit** for exactly those chunks, at most 2 MiB of body data. A responder without the descriptor checks only the wire bounds (including indices below 144) and returns Unavailable; it cannot check unknown geometry. A responder with the descriptor MUST check its profile and size before serving.

The responder sends at most one Chunk per requested index, in request order, and nothing unrequested. It MAY stop early for unavailability or resource pressure but MUST then send Complete. Complete statuses are `0 = Served`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported`, `4 = Cancelled` and `5 = TooLarge`. Served means every requested chunk was written; it does not mean the receiver accepted anything. Complete is terminal and releases unused credit, and a request never expands to further indices.

A Chunk MUST match the outstanding request's object ID, next expected index and required length, and come from the assembly's current source. It remains unverified. An identical chunk obtained through another request consumes this request's credit but MUST NOT allocate another copy or refresh the assembly's idle timer. Conflicting bytes for an already received index invalidate that source's contribution. Repeating an index within one request is a protocol violation. Complete must match the request's object ID; Served before every requested Chunk has arrived is a protocol violation. Locally discarded chunks MAY be requested again.

#### Cancel (0x05)

```text
[request_id]
```

Cancel names a request originated by its sender. The responder stops scheduling chunks and sends Complete with Cancelled for a live GetChunks request; a Chunk already being written MAY finish first. A terminal response already being written MAY finish without replacement. For GetBlockProofs not yet being answered, the responder sends the normal terminal response with Busy for every result. Cancels for unknown or completed requests are ignored.

The requester marks a cancelled request but retains its slot until a terminal response or local expiry. It MUST discard all subsequent response payloads for that request without proof verification, body hashing, retention or further recovery. A structurally valid terminal response of the expected type, with the matching object ID where present, releases the slot, including Served crossing Cancel. Responses with no live request and an ID at or below the highest issued ID are discarded, including unused gaps; ID zero or above the highest issued ID is invalid. The highest issued ID and bounded live-request map suffice. Framing, structure, count, size and rate bounds still apply. A wrong response type for a live request is a protocol violation. Cancellation does not invalidate previously retained chunks.

#### GetBlockProofs (0x06) and BlockProofs (0x07)

```text
GetBlockProofs = [request_id, selectors]
selector = [profile_id, block_hash]
BlockProofs = [request_id, results]
result = [status, descriptor_or_empty]
```

`selectors` holds 1 to `MAX_LOOKUPS` distinct entries in lexicographic `(profile_id, block_hash)` order.

Results correspond one-for-one to selectors. Statuses are `0 = OK`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported` and `4 = TooLarge`. A non-OK result carries an empty byte string. An OK block-proof descriptor MUST match the selector and the requester's receive ceiling. Unsupported means the profile is not common; Busy promises no later response.

The responder MUST return all results in one terminal response; the selector-count and descriptor-size bounds limit its size. A request never obliges a peer to prove, fetch from other peers, retain history, or allocate an object it does not hold.

### Reassembly and Source Changes

Clients MUST keep at most one assembly per object ID. Requests can interleave, but all body chunks in an assembly come from the same source peer. They MAY resume missing indices from that peer. Before switching to another source, clients MUST cancel or retire outstanding body requests and release all partial body bytes; the assembly retains its original absolute deadline and source-attempt count. The configured source-attempt budget counts restarts from the same peer; resuming missing indices is not a new attempt.

Before allocation or copying, clients MUST charge retained chunks, recovered envelopes and completion copies to the per-peer and global byte budgets. Declared lengths MUST NOT trigger allocation of the whole object. Metadata, announcements, outstanding envelope requests, source lists and verification work also need finite global and per-peer budgets. Completed objects and pending envelope recovery stay charged until validation finishes or the assembly is abandoned; sharing data MUST NOT hide pinned bytes from accounting.

Assembly timers start at first retrieval, not announcement. Idle time resets only on a newly received missing chunk from the selected source or a newly resolved missing envelope. Duplicate messages, source changes and queue moves do not extend the absolute deadline. Expiry releases bytes and metadata and cancels work no longer needed by a live assembly. Source changes after a mismatch or withholding remain subject to finite retry and work budgets.

Peers MAY evict objects and later answer Unavailable or Busy. Disconnection, expiry and insufficient local capacity do not establish object invalidity. A bounded pending-announcement cache can defer retrieval when resources are occupied; completion is not guaranteed.

### Validation and Relay

With all chunks present, the receiver MUST check the length, `content_hash` and canonical body encoding, then apply the corresponding EIP-8288 wrapper or block-proof validation.

Clients MUST NOT announce, serve through retrieval, admit or reaggregate an object before full validation. The sole early-forwarding exception is the authenticated ethp2p broadcast below; it establishes provenance, not proof validity. A content-hash mismatch discards the entire source contribution; a retry from another peer starts with no retained body bytes.

After full wrapper validation, ordinary admission is evaluated per transaction under EIP-8288. Local refusal, state changes or pool policy do not establish proof invalidity. No Complete status acknowledges admission or retention.

### Scheduling and Errors

Senders MUST apply backpressure before serializing chunks and MUST NOT queue a whole object as serialized messages. RLPx senders MUST yield at each Chunk boundary to queued messages from other protocols. Implementations SHOULD use small write windows and schedule fairly across objects, peers and capabilities.

In requested retrieval, malformed encodings, content-hash mismatches, inconsistent geometry, mismatched transaction hashes, unrequested data and invalid proofs are invalid peer data: the client MUST discard the contribution and stop the associated transfer, and MAY disable the binding for, disconnect or penalize the peer. Size violations MUST be rejected before large allocation or decompression. Unknown message IDs are protocol violations. Incompatibility, Unavailable, Busy, TooLarge, local queue exhaustion, cancellation, expiry and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior.

Verification, transaction-admission and proving queues MUST have finite concurrency and backlog, and Busy results MUST NOT create unbounded retries. Clients SHOULD throttle sources that repeatedly send invalid data or consume credit without useful progress, while tolerating isolated stalls.

### Ethp2p application profile

This optional extension combines the [ethp2p broadcast framework](https://github.com/ethp2p/ethp2p/blob/3a475961022f667778ce1c2af685388f694689ef/specs/002-ec-broadcast.md) with requested retrieval on one authenticated QUIC connection. Its explicit wire, authentication and lifecycle rules take precedence over the linked framework. Wrappers use retrieval only; block proofs MAY additionally use authenticated broadcast. All retrieval encodings, validation, credit and deadlines remain unchanged except for the explicit broadcast forwarding exception.

Every ethp2p participant MUST support retrieval ALPN `ethp2p_lean_1`. Broadcast-capable peers MAY additionally offer `ethp2p_lean_bcast_1`; the broadcast streams, handshake and early-forwarding rules below apply only when that ALPN is negotiated. Under the retrieval ALPN, peers use only the retrieval control and response streams, require no BCAST handshake, and MUST NOT send framework streams. Every supported object remains retrievable, including objects too large for broadcast; RLPx is not required when ethp2p is the common binding.

#### Discovery and authentication

An [EIP-778](./eip-778.md) v4 node record MAY advertise `leanq = [1, udp_port]`, an RLP list whose first integer is this binding's version and whose port is in `[1, 65535]`. The endpoint uses the record's `ip` or `ip6` address and the advertised port. Unknown versions are ignored. Dialers MUST verify the record's signature and MUST NOT infer support from a discovery UDP port alone.

The binding uses QUIC version 1 ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)) and TLS 1.3 with the negotiated ALPN above. Both peers MUST authenticate using the [libp2p TLS peer-authentication rules](https://github.com/libp2p/specs/blob/f201689524a23af835119834d7db75bbc71c3549/tls/tls.md#peer-authentication), with a secp256k1 identity key. The dialer MUST match that key to the signed node record's key; the certificate's separate signing key is not the node identity. The certificate's signature algorithm MUST match its SubjectPublicKeyInfo key type; receivers MUST reject a mismatch, like any other certificate parsing or verification failure, as an authentication failure. Dialers MUST send either no `server_name` extension or the fixed host name `ethp2p`, never an IP literal, which [RFC 6066](https://www.rfc-editor.org/rfc/rfc6066) forbids. Receivers MUST ignore the server name; certificates authenticate peers. The authenticated identity is also the peer's RLPx node identity for resource accounting. These ALPNs replace the libp2p ALPN; there is no additional protocol or stream-multiplexer negotiation. Application data MUST NOT use 0-RTT and MUST NOT be processed before peer authentication completes.

Failure to negotiate this binding permits bounded retry or fallback to another mutually supported binding and does not imply invalid objects. Nodes MUST account for requests, broadcast traffic, buffered bytes and verification work jointly per authenticated node key and globally. Separate connections or bindings do not grant separate per-peer budgets. Since node keys are free, receivers SHOULD limit inbound connections per IP address and subnet and reserve connection capacity for configured static peers.

#### Shared streams and requested retrieval

One dispatcher handles the framework's single-byte stream selectors `0x01` (BCAST), `0x02` (SESS) and `0x03` (CHUNK), plus this profile's `0x10` (retrieval control) and `0x11` (retrieval response). Framework messages use its [protobuf schemas](https://github.com/ethp2p/ethp2p/blob/3a475961022f667778ce1c2af685388f694689ef/broadcast/pb/broadcast.proto), each envelope prefixed by its `U32` byte length. BCAST exchanges version-1 handshakes with empty initial channel lists. Peers send that handshake and retrieval Status without waiting; both incoming messages MUST be accepted within the configured request idle timeout after authentication. Subscriptions are sent only after accepting both. Cross-stream arrival order is not guaranteed: early framework streams MUST be deferred within bounded pending-stream budgets or refused without a timing-only penalty.

Each endpoint opens exactly one outbound unidirectional **retrieval control stream**, starting with byte `0x10`, then Status as its first frame. The existing Status checks and once-per-direction rule apply. Subsequent control frames may contain only AnnounceObjects, GetBlockProofs, GetChunks or Cancel. Thus requests retain their strictly increasing IDs (gaps are allowed) and arrival order. Request IDs are scoped to a connection and direction; a response from another connection cannot satisfy a request.

Every retrieval response uses one new unidirectional **response stream**, starting with `0x11 || U64(request_id)`. It carries only the response sequence for that live request: BlockProofs; or zero or more Chunk frames followed by Complete. IDs within every frame MUST match the stream prefix, and Chunk and Complete MUST match the requested object. Chunks retain their per-request ordering. Response streams for different requests may arrive and advance in any order.

Each retrieval frame is:

```text
U8(message_id) || U32(payload_length) || RLP(message_data)
```

`payload_length` counts only the RLP bytes and MUST be in `[1, MAX_MESSAGE_BYTES]`. Receivers MUST check the ID, stream role and length before allocating or reading the payload into memory. Payloads retain canonical RLP and nesting rules. This binding uses no Snappy or other application compression, QUIC datagrams or bidirectional streams. Unknown stream types and message IDs are protocol violations.

A live request has at most one response stream. The responder MUST finish that stream with FIN immediately after its terminal response; the requester retires the request on receipt of that response and FIN. Extra bytes after a terminal response are invalid. FIN before a terminal response or a stream reset is incomplete delivery, never Served; retained chunks remain usable only for same-source resume. A response prefix for a retired request is discarded without payload work; zero or an ID above the highest issued ID is invalid. A duplicate response stream for a live request is a protocol violation.

The control stream MUST remain open for the connection's lifetime. Its closure, reset, incompatible Status or protocol violation terminates this binding and releases its requests. Partial bytes MAY be resumed from the same authenticated node within their existing assembly deadline. Changing nodes discards them under the common source-change rule.

#### Broadcast authorization and identity

Broadcast requires a locally configured **broadcast profile**, distinct from the proof `profile_id`. Before activation, the network MUST fix its 32-byte `broadcast_profile_id`, canonical signature and authorization encodings, signature verification relation and domain, consensus-context authentication, slot clock, and producer-duty rules. The profile MUST define the producer-index namespace and unambiguous duty-to-public-key mapping, including whether a block duty uses its proposer or selected builder. An ID MUST identify exactly one such configuration; changing it requires a new ID. These parameters MUST NOT come from peers. A node lacking that configuration uses retrieval only.

The authorized producer is the proposer or the builder selected for that slot and block, not any registered builder. The profile MUST bind these duties to locally authenticated consensus context and specify how the committed object matches the block. Unknown or unresolved context permits bounded deferral or retrieval, never early forwarding. A transport peer's node key or a channel subscription does not establish a producer duty.

The producer signs a manifest that commits both the original object and its coded representation:

```text
manifest = [broadcast_profile_id, fork_digest, slot, producer_index,
            consensus_context_root, block_descriptor, coding]
coding = [16, 16, shard_bytes, body_sha256, shard_hashes]
manifest_id = H("lean/1/broadcast\0" || RLP([chain_id, genesis_hash, manifest]))
preamble = RLP([manifest, signature, authorization])
channel = "lean/1/rs/" || lowerhex(H("lean/1/channel\0" ||
          RLP([chain_id, genesis_hash, broadcast_profile_id, profile_id])))
message_id = lowerhex(manifest_id)
```

`fork_digest` is four bytes and MUST match the duty's fork. `slot` and `producer_index` are unsigned 64-bit integers; the latter identifies the producer's consensus identity. `consensus_context_root` is 32 bytes and identifies the authenticated context used to resolve that duty. `signature` and `authorization` are byte strings: the former authenticates `manifest_id` under the configured producer-signature relation; the latter carries any additional evidence required by that profile. The complete preamble is at most 65,536 bytes. The existing descriptor, known-header and applicable-fork checks MUST pass before accepting it.

Peers subscribe through BCAST only to channels for block proofs and common proof profiles, under their configured broadcast profile; at most `MAX_PROFILES` channels may be subscribed per direction. SESS Open carries the preamble above. Before creating or forwarding a session, including its SESS Open, receivers MUST check its channel, manifest ID, bounds, signature and duty authorization. Senders MUST respect the receiver's `max_object_bytes`. The slot MUST be within one slot of the local current slot. All sessions for that duty expire by the start of `slot + 2`, or the assembly's existing deadline, whichever comes first.

A node MUST accept at most one distinct authenticated manifest for each `(genesis_hash, slot)`, across profiles, contexts, producers, peers and connections. Identical manifests share state. Conflicting manifests do not receive another broadcast allowance; this rule adds no consensus slashing condition. The allowance remains consumed after failure or eviction until the duty is no longer eligible. Per-duty allowances supplement finite global per-slot byte, forwarding and work budgets; they do not guarantee service. A node keeps at most `MAX_BROADCAST_SESSIONS` live sessions and refuses further manifests without penalty, leaving those objects to requested retrieval.

#### Coded shards and forwarding

Broadcast bodies are limited to `2**20` bytes. This is an optimization ceiling, not an object-validity limit: larger objects use requested retrieval. A valid block-proof object whose proof alone exceeds it, as `MAX_AGGREGATE_PROOF_BYTES` permits, travels only by retrieval. The profile fixes 16 data and 16 parity shards, adapting the framework's [Reed-Solomon strategy](https://github.com/ethp2p/ethp2p/blob/3a475961022f667778ce1c2af685388f694689ef/specs/003-ec-broadcast-rs.md) to the authenticated preamble above.

Set `shard_bytes = ceil(byte_length / 16)`, at most 65,536. Append zero bytes to the canonical body to reach `16 * shard_bytes`, then split it into consecutive data shards 0 through 15. Arithmetic uses GF(256) with polynomial `0x11d`, bytes representing field elements. Let `V[r,c] = r**c` for `0 <= r < 32`, `0 <= c < 16`, with `0**0 = 1`; the systematic generator is `G = V * inverse(V[0:16,:])`. At each byte position, row `r` of `G` applied to the 16 data bytes defines shard `r`; rows 16 through 31 are parity. `body_sha256` is SHA-256 of the unpadded body, and `shard_hashes` is the ordered list of exactly 32 SHA-256 shard digests. These hashes are distinct from the object's Keccak commitments.

CHUNK Header identifies the channel and manifest's `message_id`; `data_length` MUST equal `shard_bytes`. Its `chunk_id` is the canonical protobuf encoding of `ChunkIdent { int32 index = 1; }`: empty bytes for index zero, and `0x08 || U8(index)` for indices 1 through 31. Exactly that many raw shard bytes follow the header, then FIN; extra or truncated bytes are invalid delivery. SESS routing updates are exactly four raw bitmap bytes: shard `i` uses bit `i % 8` of byte `i / 8`, least significant bit first. An absent initial update advertises no shards; subsequent inventories accumulate by bitwise OR.

Originators MUST fully validate an object before broadcasting it. Relays MAY forward its accepted manifest and shards whose length and SHA-256 match that manifest before reconstruction or proof verification. They MUST NOT forward unchecked shards, use them for admission, or serve them as validated retrieval objects. Routing inventories MUST advertise only checked shards, retained until that session ends; eviction ends participation. A shard received twice earns no progress or additional forwarding allowance. A node that already holds the object MUST check the body against `body_sha256` and its own encoding against all 32 `shard_hashes` before forwarding or advertising shards from it; on a mismatch it forwards none of that manifest's shards, which is a signer fault.

After obtaining 16 distinct checked shards, the receiver reconstructs the body, verifies zero padding and `body_sha256`, and re-encodes it to check all 32 shard hashes. It MUST then verify the original descriptor's length, `content_hash`, encoding and block-proof validity, and the decoded object's association with the manifest's authenticated consensus context. Coding success alone is insufficient.

A reconstructing node signals completion with `RESET_STREAM(0x01)` on its outbound SESS stream to each session peer. QUIC permits only a stream's sender to reset it. The node MAY still forward shards a peer lacks according to that peer's last known inventory. A peer receiving that reset MUST stop sending shards for the session to the node and finish its own SESS stream toward it with FIN. FIN, any other reset, `STOP_SENDING`, unsubscribe or disconnection means the peer left the session; the node MUST stop sending it shards and finish its own SESS stream toward it. Every outbound SESS stream ends no later than its session. The completion signal does not acknowledge proof validity, and no other signal asserts reconstruction.

A wrong shard hash is attributable to its supplying peer. Checked shards that cannot form the committed codeword, or reconstruct an invalid object, are attributable to the manifest's signer. Signer faults are scored locally against `producer_index`, for example by deprioritizing its later manifests; they add no consensus penalty, and relays that forwarded checked shards MUST NOT be penalized, disconnected or scored for them. Failed or expired broadcasts stop forwarding and release their coded state.

A coding or context failure (shards inconsistent with the committed codeword, padding or `body_sha256`, a body not matching the descriptor's commitments, or an object not associated with the manifest's consensus context) is scoped to the manifest and MUST NOT invalidate the object ID, discard independently validated retrieval objects or prevent requested recovery. A body matching the descriptor's commitments that fails canonical encoding or block-proof validation is invalid exactly as if retrieved. Missing shards or an unusable broadcast MAY trigger ordinary GetBlockProofs/GetChunks recovery within the same assembly lifetime.

#### Cancellation and resource bounds

Cancel retains its existing meaning on the control stream, including the responder's terminal response. Sending Cancel alone does not release the request slot: a terminal response and FIN, a received reset, or local expiry does. A reset does not acknowledge admission or invalidate previously retained chunks.

At request expiry, clients retire its ID, stop associated work and cancel any response stream using QUIC `STOP_SENDING` or `RESET_STREAM`, as appropriate, with application error `0x01`. Cleanup remains charged until resources are released. An unopened or unidentified response cannot keep the request alive. Resets, stream creation, retries and switching transport MUST NOT refresh request or assembly deadlines. Known requests refused before sending a response use their normal Busy, Unsupported or TooLarge result; stream pressure alone is not peer misconduct. If no response stream is available, a refusal MAY wait in a bounded queue until capacity is available or the request expires; it MUST NOT exceed stream or queue limits to report Busy.

Clients MUST bound connections, pending streams, partial prefixes, transport receive buffers and reset-cleanup state before parsing application messages. Each connection has one retrieval control and one BCAST stream per direction; at most `MAX_REQUESTS_PER_PEER` retrieval response streams may be live per authenticated peer in each direction across connections. Unidentified streams consume a shared pending-stream budget. New stream allowances MUST be replenished only as bounded state is released; QUIC flow-control and stream-count limits MUST enforce the receiver's budgets.

QUIC has a single unidirectional stream limit, so SESS streams, which live as long as their session, compete with response and CHUNK streams. A node MUST NOT have more than `MAX_BROADCAST_SESSIONS` outbound SESS streams live on a connection, and SHOULD keep at most 16 CHUNK streams live per connection. Within that cap, senders SHOULD size the live CHUNK streams to a peer to the path's bandwidth-delay product rather than a smaller fixed window. Receivers SHOULD grant an initial unidirectional stream limit (`initial_max_streams_uni`) of at least `2 + MAX_REQUESTS_PER_PEER + MAX_BROADCAST_SESSIONS + 16`, that is 26, so that broadcast cannot exhaust the allowance retrieval needs. Within the shared byte budgets, receivers SHOULD allow a full GetChunks response per response stream and size aggregate receive credit to the path's bandwidth-delay product. Unread transport bytes and application buffers MUST be accounted together; flow-control credit MUST NOT permit exceeding those budgets. Smaller windows can limit throughput as round-trip time grows.

An incomplete stream prefix or first framework envelope expires within the configured request idle timeout of stream acceptance. Once identified, a response stream uses its request's original deadlines, and a shard body uses its duty and assembly deadlines. Every later incomplete framework envelope or retrieval control frame expires within the configured request idle timeout of its first byte; this does not expire an otherwise idle control stream. Trickle bytes alone MUST NOT refresh these parsing deadlines.

Framework envelopes MUST be bounded by `MAX_MESSAGE_BYTES` before allocation; preambles and shard bodies retain their tighter limits. Clients MUST also bound subscriptions, pending SESS/CHUNK streams, duplicate traffic, signature checks, coding work and per-slot forwarding. A CHUNK stream naming an unknown manifest MAY be deferred within those budgets for at most `MAX_SHARD_DEFERRAL_SECONDS` after its header arrives, then refused without penalty. Geometry MUST be checked before initializing a coder; decoded and re-encoded buffers remain charged through final validation. No session creation, reset, duplicate, routing update or peer change renews the duty allowance or its expiry.

Implementations MUST reserve receive and send capacity for both control streams, apply backpressure before serializing responses or shards, and schedule fairly between retrieval, broadcast and other traffic. QUIC streams share connection bandwidth and congestion control; stream isolation does not replace byte or work budgets.

#### Reassembly and relay

All bindings and broadcast manifests contribute to the same assembly indexed by `object_id`, with one original absolute deadline. Coded shards are kept separately by manifest ID and MUST NOT be mixed across manifests or treated as validated retrieval objects. The first accepted manifest starts an assembly if none exists; each new checked shard may advance its idle timer, subject to the duty expiry. Decoding and switching to retrieval do not renew its absolute lifetime. Both representations count toward the shared byte budget until released; successfully reconstructed bytes enter the common object store only after canonical integrity checks. Nodes SHOULD release the coded shards' incomplete-assembly charge on reconstruction. A codeword kept for forwarding, at most `32 * shard_bytes` bytes, is then charged to a broadcast budget bounded by `MAX_BROADCAST_SESSIONS` until its session ends.

Announcing and broadcasting the same object transfers it twice. A receiver holding an accepted manifest for an object MAY defer requesting its chunks while new checked shards arrive, and SHOULD fall back to retrieval once none has arrived for about one round-trip time; deferral extends no deadline. Nodes SHOULD NOT announce the object to a peer still participating in that session.

Requested chunks retain one unverified copy per index from the selected source node, shared across its bindings. Credit and response ordering are tracked separately for each request; duplicate bytes consume request credit without refreshing assembly progress. Closing a connection preserves same-node resume; changing the source node discards partial retrieval bytes. Authenticated broadcast shards are separate and can come from multiple relays. Only fully validated objects may be announced, served through retrieval or admitted; broadcast provenance does not establish an inclusion obligation.

## Rationale

Announcement followed by requested retrieval follows [EIP-2464](./eip-2464.md); size-aware selection follows [EIP-5793](./eip-5793.md). Request IDs follow [EIP-2481](./eip-2481.md), with strictly increasing IDs allowing stale responses to be discarded without retaining every retired ID.

Single-source assembly makes corrupt data attributable to its sender. Since integrity is checked against the complete content hash, switching sources restarts retrieval; requests to the same source can resume missing chunks.

Hash-only wrappers keep identity independent of peers' envelope caches and avoid embedding thousands of transactions. The object-size ceiling accommodates EIP-8288 wrappers; it is not a recommended batch size. Deriving profile IDs from locally configured keys avoids a separate verifier registry.

Validation before relay adds a full download and proof check at every hop. Large wrappers cannot be assumed to propagate within the aggregation interval; batch sizes require latency measurements.

Separate block-proof delivery is experimental: ordinary block bodies already carry the proof, so broadcast can duplicate those bytes. Activation requires a concrete block-acquisition strategy and end-to-end measurements demonstrating a benefit while preserving ordinary body availability.

Ethp2p isolates ordered retrieval control from independent response streams. Authenticated block-duty broadcast additionally permits early shard forwarding with 16-of-32 reconstruction and a 1 MiB body ceiling. Requested retrieval retains the 9 MiB ceiling and single-source rule. Re-encoding all shards checks codeword consistency and prevents attributing a producer's inconsistent coding to honest relays. Four live sessions cover the three eligible block slots with margin.

## Backwards Compatibility

Peers without this protocol can continue using existing protocols. Peers offering wrappers also serve their retained envelopes through ETH, including envelopes outside the admitted transaction pool.

Authenticated broadcast additionally requires the configured producer-authorization profile. Retrieval can activate without broadcast, but ethp2p-only operation still requires the envelope-retrieval binding described above.

| Duplicate chunk through another request to the same source | Consume credit, retain one copy, no renewed assembly progress |
| Chunk bytes conflict with an already retained index | Discard the source contribution |

| Cancel crosses the last Chunk and Served | Discard post-cancellation payloads; terminal response releases the slot |
| BlockProofs arrives after cancellation | Check terminal structure and release slot without using results |
| Late response after expiry; requester and responder expire at different times | Discard retired responses; timing alone incurs no penalty |
| A body fails its content hash; another source offers the same descriptor | Discard partial bytes, retry within the original deadline and attempt bound |
| Source changes or reconnects; duplicate announcements or queue moves | No extended absolute lifetime or multiplied budgets |
| Requests across many peers would exceed the global byte ceiling | Refuse or defer before allocation |
| Complete body waits for verification or envelope recovery | Remains charged and expires normally |
| Envelope retained outside the admitted pool is requested through ETH | Serve it while offering its validated wrapper |

Scheduling tests should cover bounded retry, completion-copy pressure, verification queues and control messages between chunk writes. Proof-verifier interoperability requires EIP-8288 profiles and test vectors.

### Ethp2p conformance

The Cancel frame for request 7 is `0500000002c107`; the retrieval control prefix is `10` and a response prefix for request 7 is `110000000000000007`. [The ethp2p framing checks](../assets/eip-8437/check_ethp2p.py) cover these encodings, fragmented reads, stream roles, payload ceilings and truncated frames. [Broadcast checks](../assets/eip-8437/check_broadcast.py) cover the fixed code, commitments, reconstruction and shard encodings; neither checker establishes producer-signature or network interoperability. Implementations must additionally cover:

| Case | Expected result |
| --- | --- |

| Certificate signature algorithm does not match its key type | Reject as an authentication failure, not an unhandled error |
| ClientHello carries no server name, `ethp2p` or another name | Ignore it; authenticate only by certificate |
| Ethp2p is the common binding but QUIC is unavailable or the bind fails | Fail to start or disable the protocol and report it; never continue on other bindings alone |
| Response streams for requests 2 and 1 arrive in that order | Accept independently; the control-stream requests themselves remain strictly increasing with gaps allowed |
| Wrong response ID, object ID or response type; two streams for one live request | Reject the contribution as a protocol violation |
| Partial prefix, oversized frame, extra bytes after a terminal response, or control-stream closure | Enforce bounds or terminate the binding as specified; retain chunks for same-source resume |
| FIN or reset before Complete; Cancel races Complete and FIN | Incomplete delivery or normal retirement, never premature Served or duplicate slot release |
| A known response stream resets after Cancel | Release the slot without waiting for a Complete message |
| Connection closes after some chunks; retrieval continues over RLPx | Same object ID and deadline; another source requires discarding partial body bytes |
| Same source sends a chunk over both bindings or opens more connections | One retained copy; shared per-node budgets and unchanged assembly progress for duplicates |
| Partial stream prefixes or repeated resets consume resources | Enforce pending-stream, cleanup and age limits without unbounded state |
| All chunks arrive but the object proof fails | Reject; no announcement or serving over either binding |
| Only retrieval ALPN is negotiated | Wrapper retrieval only; no block-proof lookups, BCAST handshake or framework streams |
| BCAST/SESS/CHUNK arrives before the peer's Status due to cross-stream ordering | Bound deferral or refusal; no timing-only penalty or early forwarding |
| Wrong channel, manifest ID, signature, fork, duty or unknown consensus context | No broadcast session forwarding or shard allocation |
| A wrapper or a body above 1 MiB is offered for broadcast | Refuse broadcast; valid objects remain retrievable within their normal limits |
| Descriptor has neither three nor four fields, or a block descriptor arrives without the broadcast ALPN | Reject |
| Authorized manifests conflict for one duty, including across profiles, connections or context roots | One broadcast allowance; no automatic invalidation of either underlying object |
| Manifest or shard is repeated; a session reconnects or changes peers | No additional allowance or renewed expiry |
| Shard hash mismatches; checked shards decode to inconsistent coding or an invalid object | Attribute the former to the supplying peer and the latter to the manifest signer; never penalize relays |
| Node already holding the object receives a manifest whose shard hashes differ from its encoding | Forward and advertise none of that manifest's shards |
| Reconstructed body fails coding or context checks; or matches the descriptor but fails encoding or block-proof validation | Former: scoped to the manifest, object still retrievable; latter: object invalid |
| CHUNK names a manifest still unknown after `MAX_SHARD_DEFERRAL_SECONDS` | Refuse without penalty |
| `MAX_BROADCAST_SESSIONS` sessions are live; a peer completes or leaves one | Refuse further manifests without penalty; finish the SESS stream toward that peer, returning its stream allowance |
| Object is announced while its broadcast session delivers shards | Chunk requests may wait; retrieve after about one round-trip time without a new shard |
| Broadcast fails but same-source partial retrieval bytes exist | Keep same-source partial bytes; use the original assembly deadline |
| Reconstructed codeword matches SHA-256 but not the original descriptor | Reject; coding integrity cannot replace canonical object checks |
| SESS completion reset arrives before proof verification finishes | Stop sending shards and finish the SESS stream toward that peer; do not infer validity, admission or inclusion obligations |
| Common binding changes at a coordinated activation | All participating nodes retain a common path; retrieval works without requiring RLPx fallback |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof. Announcements and chunks therefore establish no validity, and full validation precedes retrieval relay; only authenticated broadcast shards have the specified exception. Finite per-peer and global byte, recovery and work budgets remain necessary against many peer identities; absolute deadlines bound withholding and slow streams.

Arithmetic on counts, offsets, lengths and credit must be checked before allocation, and proof decoders need their own resource bounds. Invalid proof checks can cost real work without corresponding sender effort.

RLPx chunking permits interleaving but does not remove TCP head-of-line blocking. QUIC isolates streams under shared congestion and resource limits. Authenticated broadcast bounds early forwarding by producer duty; a checked shard still does not establish proof validity. Neither binding guarantees completion within a slot.
