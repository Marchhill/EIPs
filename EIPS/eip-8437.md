## Abstract

This EIP defines shared object identities and requested retrieval for [EIP-8288](./eip-8288.md) wrappers and optional block proofs, over `lean/1` devp2p or an ethp2p QUIC binding. Both use bounded chunks and full validation before relay. Transaction envelopes use ETH retrieval; inclusion-list proofs remain on the CL gossip and Engine API path. No consensus rules change.

## Motivation

Dependency witnesses and aggregated proofs can be much larger than ordinary transactions. Whole-object messages occupy the connection while being written and make interrupted retrieval expensive. Unsolicited objects also consume receiver resources before the receiver decides whether it needs them.

Requested chunks bound each transfer and let proof traffic interleave with other messages. Hash-only wrappers keep object identity independent of which transactions each peer already holds.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Scope and Constants

EIP-8288 defines object encoding, validity and proof limits. This EIP only transfers valid wrappers and block proofs. Inclusion-list proofs travel with authenticated consensus-layer IL gossip and reach the execution layer through the Engine API; they have no separate object kind here.

The network's deployment configuration MUST designate a common binding, RLPx or the ethp2p profile below, which all participating nodes MUST support. Additional bindings are optional. A migration MUST preserve a common binding until the coordinated transition. A node unable to run it MUST fail to start or disable this protocol and report nonparticipation; silently using other bindings alone is not permitted. Ethp2p-only deployment also requires a network-specified, interoperable binding for ETH envelope-retrieval semantics; this EIP adds no transaction-retrieval messages.

| Name | Value | Meaning |
| --- | --- | --- |
| `CAPABILITY` | `lean/1` | Capability name and version |
| `MESSAGE_COUNT` | `8` | Relative message IDs `0x00` through `0x07` |
| `CHUNK_BYTES` | `65536` | Fixed object chunk size |
| `MAX_OBJECT_BYTES` | EIP-8288 `MAX_WRAPPER_BYTES` | 9 MiB transport ceiling |
| `MAX_MESSAGE_BYTES` | `131072` | Uncompressed message-data ceiling |
| `MAX_RLP_DEPTH` | `8` | Maximum nesting of transport lists |
| `MAX_PROFILES` | `16` | Profile IDs in Status |
| `MAX_ANNOUNCEMENTS` | `64` | Descriptors per announcement |
| `MAX_LOOKUPS` | `16` | Selectors per GetObjects request |
| `MAX_CHUNKS_PER_REQUEST` | `32` | Chunk indices per request |
| `MAX_REQUESTS_PER_PEER` | `4` | Outstanding requests per direction |
| `MAX_BUFFERED_BYTES_PER_PEER` | `2 * MAX_OBJECT_BYTES` | Unvalidated bytes charged to one source |
| `MAX_BUFFERED_BYTES` | `8 * MAX_OBJECT_BYTES` | Global unvalidated-byte ceiling |

These are transport ceilings, not consensus validity limits. A client MAY enforce lower local limits and refuse work without penalizing the peer. A transport refusal MUST NOT be treated as an invalid transaction or block. Request limits do not reserve an entire object per request; all requests share the byte budgets above.

### Local Resource Policy

Clients MUST configure finite request and assembly idle and absolute lifetimes, and a finite source-attempt budget. RECOMMENDED defaults are request idle/absolute lifetimes of 30/120 seconds, assembly idle/absolute lifetimes of 30/300 seconds, and three source attempts. These are local policy, not negotiated wire limits. The chosen limits apply for each request or assembly's lifetime; retries and source changes MUST NOT renew them. Different local limits are not peer misbehavior.

### Encoding

Message data and object bodies use canonical RLP with exactly the field counts specified. Integers use the shortest unsigned encoding, with zero as the empty string; stated widths are range bounds, not fixed-width fields. Leading zeros, extra fields, trailing bytes, nonminimal length prefixes and wrong list/string types are invalid. Hashes are exactly 32 bytes. Byte strings sort lexicographically; tuples sort by their fields, comparing integers numerically. Lists MUST be checked against their count bounds before allocating elements; the outermost RLP list has depth one and nested transport lists MUST NOT exceed `MAX_RLP_DEPTH`. Transaction envelopes and proofs are opaque byte strings at this layer, parsed afterward by their own bounded parsers.

`H` is Keccak-256, not SHA3-256. It is distinct from EIP-8288's `DEPS_HASH`, which this EIP uses only through `get_deps_hash`. `RLP(x)` is canonical RLP. In framing, `U8`, `U32` and `U64` are fixed-width big-endian unsigned integers. In commitment formulas, `||` is byte concatenation and a domain label is its ASCII bytes followed by one zero byte.

For the RLPx binding, [RLPx](https://github.com/ethereum/devp2p/blob/76cf0a141e8aa8616e3305738d51101945387d3c/rlpx.md) compression, encryption, message-ID multiplexing and authentication are unchanged. Implementations MUST check the advertised uncompressed size before decompression and reject messages exceeding `MAX_MESSAGE_BYTES`. Requested-retrieval body bytes travel only in Chunk messages, one chunk per message; there is no whole-object message, and implementations MUST NOT rely on RLPx frame fragmentation to carry an object.

### Capability and Profiles

For RLPx, peers negotiate capability name `lean`, version `1`, through Hello; ethp2p uses the application profile below. All eight message IDs are reserved even if an optional object kind is unsupported or the capability is disabled after Status. Both bindings MUST send Status without waiting for the peer's Status. A peer MUST NOT send any other retrieval message before accepting the peer's Status.

A **profile ID** identifies the verification key for an object's recursive STARK:

```text
profile_id = H("lean/1/profile\0" || AGGREGATED_VK)
```

`AGGREGATED_VK` uses the canonical byte encoding fixed by the activated EIP-8288 fork, never a client-specific key serialization. It fixes the cryptographic profile, including dependency hashing and encodings, verifier parameters and bounds, and the circuit's `enabled_schemes` and verification relations. Changing that scheme set requires a new key and therefore a new `profile_id`. Clients derive profile IDs from local fork configuration, never peer-supplied keys. A **common profile** appears in both Status messages and is supported locally.

A profile selects a verifier, not a fork or a valid chain. The receiver MUST check it against the applicable fork: the known block header's fork for kind 2, and the local target block for kind 1. Forks sharing a key share the cryptographic profile and enabled schemes but may have different transaction or admission rules outside the circuit. Status MAY list known past and future profiles; activation does not update Status, and peers reconnect if new profiles must be advertised. A profile inappropriate for the receiver's target context is not by itself peer misbehavior.

Proof-format and resource checks are those of EIP-8288 under the selected profile, including checks before decoding or verification. Transport size ceilings do not replace them.

Status is sent exactly once in each direction:

```text
Status (0x00) = [1, chain_id, genesis_hash, profiles, kinds, max_object_bytes]
```

- The first field is the Status version, `1`.
- `chain_id` is an unsigned integer less than `2**256`.
- `genesis_hash` is 32 bytes.
- `profiles` is a nonempty, strictly ascending list of at most `MAX_PROFILES` 32-byte profile IDs.
- `kinds` is a bit mask in which bit `kind - 1` advertises support for that kind. Bit zero MUST be set and bits above one MUST be zero.
- `max_object_bytes` is an integer in `[1, MAX_OBJECT_BYTES]`: a local receive ceiling, not a promise to accept every smaller object.

The chain ID and genesis hash MUST match local configuration, and at least one profile MUST be common. An incompatible Status disables this capability; clients SHOULD keep other protocols on the connection. Malformed or repeated Status, or other messages received before Status, are protocol violations.

### Object Kinds and Canonical Bodies

An **object** consists of a descriptor and a canonical body of 1 to `MAX_OBJECT_BYTES` bytes.

#### Kind 1: Mempool Wrapper

The context is `[]`. The body MUST be a valid EIP-8288 wrapper in its canonical hash-only encoding. There is no full-envelope variant on this protocol.

After checking body integrity and encoding, receivers SHOULD verify the claimed dependency proof before recovering missing envelopes. Every transaction hash still needs resolution and full EIP-8288 wrapper validation before admission, reaggregation or relay. A preliminary proof check does not authenticate the transaction-hash list. Failed recovery leaves the object incomplete rather than invalid.

Envelope recovery uses the negotiated ETH `GetPooledTransactions`/`PooledTransactions` messages. A node offering a wrapper MUST serve its retained envelopes through that interface even when they are absent from its admitted transaction pool. Requests and retention remain bounded; they do not trigger historical searches or recursive peer fetches. Receivers extract the canonical [EIP-2718](./eip-2718.md) envelope from the ETH representation and check its hash. Peers MUST support the network's compatible ETH envelope-retrieval binding to enable kind 1; it is not provided by the lean QUIC stream profile.

#### Kind 2: Block Proof

```text
context = [block_hash]
body = RLP([stark_proof])
```

The receiver MUST obtain the ordinary block header before requesting chunks, check the profile against its fork, and after retrieval check `H(stark_proof)` against the header's `stark_proof_hash`. The one-element list keeps the transport body nonempty for an empty proof. Full validation also requires the block transactions and all EIP-8288 block-proof checks; the proof alone does not establish block validity or canonical-chain membership.

This optional path retrieves only the proof, for independent recovery or fallback after an incomplete proof broadcast, without requesting the rest of the block again. The proof remains in the block body and execution payload. Ordinary block acquisition already supplying those bytes MUST NOT trigger a second required transfer. There is no header skeleton and no change to header or block-body encoding.

### Descriptors and Identity

```text
descriptor = [kind, profile_id, context, byte_length, content_hash]
content_hash = H(body)
object_id = H("lean/1/object\0" || RLP(descriptor))
```

`kind` is 1 or 2; `context` has that kind's form. `byte_length` is a 64-bit unsigned integer within the object bounds. A descriptor is at most 256 encoded bytes. Receivers MUST check its encoding, profile, context and size before requesting chunks. The same wrapper body produces the same identity for every peer; different proof bytes still identify different objects.

An **assembly** is a receiver's partial copy of an object, keyed by `object_id`; requests are keyed by `(connection, request_id)`. A repeated descriptor MUST NOT create another assembly. A receiver uses one source peer at a time for an assembly, without mixing unverified body bytes from different peers.

### Chunk Geometry

```text
N = ceil(byte_length / CHUNK_BYTES)
chunk[i] = body[i * CHUNK_BYTES : min((i + 1) * CHUNK_BYTES, byte_length)]
```

Thus `1 <= N <= 144`. Every chunk except the last is exactly `CHUNK_BYTES`; the last is `byte_length - (N - 1) * CHUNK_BYTES` bytes. There are no chunk proofs: bytes remain untrusted until the complete body matches `content_hash`. A source switch discards all partial body bytes, while a retry from the same source may request only missing indices.

### Messages and Request Lifecycle

RLPx IDs are relative to the capability's negotiated message offset; ethp2p uses them directly:

| ID | Message | Direction |
| --- | --- | --- |
| `0x00` | Status | Both |
| `0x01` | AnnounceObjects | Both |
| `0x02` | GetObjects | Request |
| `0x03` | Objects | Response |
| `0x04` | GetChunks | Request |
| `0x05` | Chunk | Response |
| `0x06` | Complete | Terminal GetChunks response |
| `0x07` | Cancel | Requester to responder |

Request IDs are 64-bit unsigned integers. On each connection a peer MUST assign positive, strictly increasing IDs to requests of both types in send order, never wrapping or reusing an ID. Gaps are allowed; each direction has its own sequence, and responses echo the request's ID. A new incoming ID no greater than the preceding one is a protocol violation, even if the request is refused. Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` locally live requests per direction. Responders return Busy for requests they cannot accept. Receiving a request while at the local limit MUST NOT by itself incur a penalty, since expiry times can differ.

Each endpoint measures deadlines with its own monotonic clock: the requester starts when sending the request, the responder when receiving it. Request idle time resets only when receiving a valid first response for a requested result, or when writing that result on the responder. A chunk already obtained through another request to the same source can advance a request without advancing the assembly. Each endpoint retires the request at its idle or absolute deadline, whichever comes first; no synchronized expiry is assumed. Disconnection releases request state. Neither requests nor cancellation reset an assembly's absolute age.

#### AnnounceObjects (0x01)

```text
[descriptor, ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `object_id` order. A sender MUST announce only objects it holds in full and has validated as specified for their kind, including, for kind 2, the block itself. Announced objects MUST use a common profile and a kind supported by both peers, and fit the receiver's advertised ceiling. Receivers MAY ignore other descriptors without allocating assemblies.

Announcements neither require receiver action nor establish validity. Repetition earns no credit or retention. Peers SHOULD suppress unchanged announcements and rotate bounded selections fairly across useful objects. A receiver that wants an announced object but is at its request or assembly limits SHOULD keep it pending in a bounded cache and retrieve it when capacity frees, since the announcement may not be repeated.

#### GetObjects (0x02) and Objects (0x03)

```text
GetObjects = [request_id, selectors]
selector = [kind, profile_id, lookup_key]
Objects = [request_id, results]
result = [status, descriptor_or_empty]
```

`selectors` holds 1 to `MAX_LOOKUPS` distinct entries in ascending `(kind, profile_id, lookup_key)` order. `lookup_key` is the object ID for kind 1 or block hash for kind 2. There is no transaction-envelope lookup.

Results correspond one-for-one to selectors. Statuses are `0 = OK`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported` and `4 = TooLarge`. A non-OK result carries an empty byte string. An OK descriptor MUST match the selector and the requester's receive ceiling. Unsupported means the profile is not common or the kind is unsupported; Busy promises no later response.

The responder MUST return all results in one terminal response; the selector-count and descriptor-size bounds limit its size. A request never obliges a peer to prove, fetch from other peers, retain history, or allocate an object it does not hold.

#### GetChunks (0x04), Chunk (0x05), and Complete (0x06)

```text
GetChunks = [request_id, object_id, indices]
Chunk = [request_id, object_id, index, chunk_bytes]
Complete = [request_id, object_id, status]
```

The requester MUST already hold a well-formed descriptor using a common profile and a kind supported by both peers, within its receive ceiling. `indices` is a strictly ascending list of 1 to `MAX_CHUNKS_PER_REQUEST` 32-bit integers less than `N`. The request grants **credit** for exactly those chunks, at most 2 MiB of body data. A responder without the descriptor checks only the wire bounds (including indices below 144) and returns Unavailable; it cannot check unknown geometry. A responder with the descriptor MUST check its profile, kind and size before serving.

The responder sends at most one Chunk per requested index, in request order, and nothing unrequested. It MAY stop early for unavailability or resource pressure but MUST then send Complete. Complete statuses are `0 = Served`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported`, `4 = Cancelled` and `5 = TooLarge`. Served means every requested chunk was written; it does not mean the receiver accepted anything. Complete is terminal and releases unused credit, and a request never expands to further indices.

A Chunk MUST match the outstanding request's object ID, next expected index and required length, and come from the assembly's current source. It remains unverified. An identical chunk obtained through another request consumes this request's credit but MUST NOT allocate another copy or refresh the assembly's idle timer. Conflicting bytes for an already received index invalidate that source's contribution. Repeating an index within one request is a protocol violation. Complete must match the request's object ID; Served before every requested Chunk has arrived is a protocol violation. Locally discarded chunks MAY be requested again.

#### Cancel (0x07)

```text
[request_id]
```

Cancel names a request originated by its sender. The responder stops scheduling chunks and sends Complete with Cancelled for a live GetChunks request; a Chunk already being written MAY finish first. A terminal response already being written MAY finish without replacement. For GetObjects not yet being answered, the responder sends the normal terminal response with Busy for every result. Cancels for unknown or completed requests are ignored.

The requester marks a cancelled request but retains its slot until a terminal response or local expiry. It MUST discard all subsequent response payloads for that request without proof verification, body hashing, retention or further recovery. A structurally valid terminal response of the expected type, with the matching object ID where present, releases the slot, including Served crossing Cancel. Responses with no live request and an ID at or below the highest issued ID are discarded, including unused gaps; ID zero or above the highest issued ID is invalid. The highest issued ID and bounded live-request map suffice. Framing, structure, count, size and rate bounds still apply. A wrong response type for a live request is a protocol violation. Cancellation does not invalidate previously retained chunks.

### Reassembly and Source Changes

Clients MUST keep at most one assembly per object ID. Requests can interleave, but all body chunks in an assembly come from the same source peer. They MAY resume missing indices from that peer. Before switching to another source, clients MUST cancel or retire outstanding body requests and release all partial body bytes; the assembly retains its original absolute deadline and source-attempt count. The configured source-attempt budget counts restarts from the same peer; resuming missing indices is not a new attempt.

Before allocation or copying, clients MUST charge retained chunks, recovered envelopes and completion copies to the per-peer and global byte budgets. Declared lengths MUST NOT trigger allocation of the whole object. Metadata, announcements, outstanding envelope requests, source lists and verification work also need finite global and per-peer budgets. Completed objects and pending envelope recovery stay charged until validation finishes or the assembly is abandoned; sharing data MUST NOT hide pinned bytes from accounting.

Assembly timers start at first retrieval, not announcement. Idle time resets only on a newly received missing chunk from the selected source or a newly resolved missing envelope. Duplicate messages, source changes and queue moves do not extend the absolute deadline. Expiry releases bytes and metadata and cancels work no longer needed by a live assembly. Source changes after a mismatch or withholding remain subject to finite retry and work budgets.

Peers MAY evict objects and later answer Unavailable or Busy. Disconnection, expiry and insufficient local capacity do not establish object invalidity. A bounded pending-announcement cache can defer retrieval when resources are occupied; completion is not guaranteed.

### Validation and Relay

With all chunks present, the receiver MUST check the length, `content_hash` and canonical body encoding, then apply the kind's validation. Sender-supplied metadata MUST NOT substitute for these checks.

Clients MUST NOT announce, serve, admit or reaggregate an object before full validation. A content-hash mismatch discards the entire source contribution; a retry from another peer starts with no retained body bytes.

After full wrapper validation, ordinary admission is evaluated per transaction under EIP-8288. Local refusal, state changes or pool policy do not establish proof invalidity. No Complete status acknowledges admission or retention.

### Scheduling and Errors

Senders MUST apply backpressure before serializing chunks and MUST NOT queue a whole object as serialized messages. RLPx senders MUST yield at each Chunk boundary to queued messages from other protocols. Implementations SHOULD use small write windows and schedule fairly across objects, peers and capabilities.

In requested retrieval, malformed encodings, content-hash mismatches, inconsistent geometry, mismatched transaction hashes, unrequested data and invalid proofs are invalid peer data: the client MUST discard the contribution and stop the associated transfer, and MAY disable the binding for, disconnect or penalize the peer. Size violations MUST be rejected before large allocation or decompression. Unknown message IDs are protocol violations. Incompatibility, Unavailable, Busy, TooLarge, local queue exhaustion, cancellation, expiry and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior.

Verification, transaction-admission and proving queues MUST have finite concurrency and backlog, and Busy results MUST NOT create unbounded retries. Clients SHOULD throttle sources that repeatedly send invalid data or consume credit without useful progress, while tolerating isolated stalls.

### Ethp2p application profile

This binding carries the same eight retrieval messages over authenticated QUIC. Object encodings, commitments, validation, credit and deadlines are unchanged. Both object kinds use requested retrieval; RLPx is not required when ethp2p is the common binding.

#### Discovery and authentication

An [EIP-778](./eip-778.md) v4 node record MAY advertise `leanq = [1, udp_port]`, an RLP list whose first integer is this binding's version and whose port is in `[1, 65535]`. The endpoint uses the record's `ip` or `ip6` address and the advertised port. Unknown versions are ignored. Dialers MUST verify the record's signature and MUST NOT infer support from a discovery UDP port alone.

The binding uses QUIC version 1 ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)) and TLS 1.3 with the ALPN identifier `ethp2p_lean_1`. Both peers MUST authenticate using the [libp2p TLS peer-authentication rules](https://github.com/libp2p/specs/blob/f201689524a23af835119834d7db75bbc71c3549/tls/tls.md#peer-authentication), with a secp256k1 identity key. The dialer MUST match that key to the signed node record's key; the certificate's separate signing key is not the node identity. The certificate's signature algorithm MUST match its SubjectPublicKeyInfo key type; receivers MUST reject a mismatch, like any other certificate parsing or verification failure, as an authentication failure. Dialers MUST send either no `server_name` extension or the fixed host name `ethp2p`, never an IP literal, which [RFC 6066](https://www.rfc-editor.org/rfc/rfc6066) forbids. Receivers MUST ignore the server name; certificates authenticate peers. The authenticated identity is also the peer's RLPx node identity for resource accounting. This ALPN replaces the libp2p ALPN; there is no additional protocol or stream-multiplexer negotiation. Application data MUST NOT use 0-RTT and MUST NOT be processed before peer authentication completes.

Failure to negotiate this binding permits bounded retry or fallback to another mutually supported binding and does not imply invalid objects. Nodes MUST account for requests, buffered bytes and verification work jointly per authenticated node key and globally. Separate connections or bindings do not grant separate per-peer budgets. Since node keys are free, receivers SHOULD limit inbound connections per IP address and subnet and reserve connection capacity for configured static peers.

#### Shared streams and requested retrieval

Unidirectional streams begin with a single-byte selector: `0x10` for retrieval control or `0x11` for a retrieval response. The peer's Status MUST be accepted within the configured request idle timeout after authentication. Other stream selectors require a separately negotiated extension and MUST NOT be sent under this binding.

Each endpoint opens exactly one outbound unidirectional **retrieval control stream**, starting with byte `0x10`, then Status as its first frame. The existing Status checks and once-per-direction rule apply. Subsequent control frames may contain only AnnounceObjects, GetObjects, GetChunks or Cancel. Thus requests retain their strictly increasing IDs (gaps are allowed) and arrival order. Request IDs are scoped to a connection and direction; a response from another connection cannot satisfy a request.

Every retrieval response uses one new unidirectional **response stream**, starting with `0x11 || U64(request_id)`. It carries only the response sequence for that live request: Objects; or zero or more Chunk frames followed by Complete. IDs within every frame MUST match the stream prefix, and Chunk and Complete MUST match the requested object. Chunks retain their per-request ordering. Response streams for different requests may arrive and advance in any order.

Each retrieval frame is:

```text
U8(message_id) || U32(payload_length) || RLP(message_data)
```

`payload_length` counts only the RLP bytes and MUST be in `[1, MAX_MESSAGE_BYTES]`. Receivers MUST check the ID, stream role and length before allocating or reading the payload into memory. Payloads retain canonical RLP and nesting rules. This binding uses no Snappy or other application compression, QUIC datagrams or bidirectional streams. Unknown stream types and message IDs are protocol violations.

A live request has at most one response stream. The responder MUST finish that stream with FIN immediately after its terminal response; the requester retires the request on receipt of that response and FIN. Extra bytes after a terminal response are invalid. FIN before a terminal response or a stream reset is incomplete delivery, never Served; retained chunks remain usable only for same-source resume. A response prefix for a retired request is discarded without payload work; zero or an ID above the highest issued ID is invalid. A duplicate response stream for a live request is a protocol violation.

The control stream MUST remain open for the connection's lifetime. Its closure, reset, incompatible Status or protocol violation terminates this binding and releases its requests. Partial bytes MAY be resumed from the same authenticated node within their existing assembly deadline. Changing nodes discards them under the common source-change rule.

#### Cancellation and resource bounds

Cancel retains its existing meaning on the control stream, including the responder's terminal response. Sending Cancel alone does not release the request slot: a terminal response and FIN, a received reset, or local expiry does. A reset does not acknowledge admission or invalidate previously retained chunks.

At request expiry, clients retire its ID, stop associated work and cancel any response stream using QUIC `STOP_SENDING` or `RESET_STREAM`, as appropriate, with application error `0x01`. Cleanup remains charged until resources are released. An unopened or unidentified response cannot keep the request alive. Resets, stream creation, retries and switching transport MUST NOT refresh request or assembly deadlines. Known requests refused before sending a response use their normal Busy, Unsupported or TooLarge result; stream pressure alone is not peer misconduct. If no response stream is available, a refusal MAY wait in a bounded queue until capacity is available or the request expires; it MUST NOT exceed stream or queue limits to report Busy.

Clients MUST bound connections, pending streams, partial prefixes, transport receive buffers and reset-cleanup state before parsing application messages. Each connection has one retrieval control stream per direction; at most `MAX_REQUESTS_PER_PEER` retrieval response streams may be live per authenticated peer in each direction across connections. Unidentified streams consume a shared pending-stream budget. New stream allowances MUST be replenished only as bounded state is released; QUIC flow-control and stream-count limits MUST enforce the receiver's budgets.

Receivers SHOULD grant an initial unidirectional stream limit (`initial_max_streams_uni`) of at least `1 + MAX_REQUESTS_PER_PEER`, that is five, for control and concurrent responses. Within the shared byte budgets, receivers SHOULD allow a full GetChunks response per response stream and size aggregate receive credit to the path's bandwidth-delay product. Unread transport bytes and application buffers MUST be accounted together; flow-control credit MUST NOT permit exceeding those budgets. Smaller windows can limit throughput as round-trip time grows.

An incomplete stream prefix expires within the configured request idle timeout of stream acceptance. Once identified, a response stream uses its request's original deadlines. Each incomplete retrieval control frame expires within that timeout of its first byte; this does not expire an otherwise idle control stream. Trickle bytes MUST NOT refresh these parsing deadlines.

Implementations MUST reserve receive and send capacity for control messages, apply backpressure before serializing responses, and schedule fairly between retrieval and other traffic. QUIC streams share connection bandwidth and congestion control; stream isolation does not replace byte or work budgets.

#### Reassembly and relay

All bindings share the assembly indexed by `object_id` and its original absolute deadline. Requested chunks retain one unverified copy per index from the selected source node, shared across its bindings. Credit and response ordering are tracked separately for each request; duplicate bytes consume request credit without refreshing assembly progress. Closing a connection preserves same-node resume; changing the source node discards partial retrieval bytes. Only fully validated objects may be announced, served or admitted.

## Rationale

Announcement followed by requested retrieval follows [EIP-2464](./eip-2464.md); size-aware selection follows [EIP-5793](./eip-5793.md). Request IDs use the correlation pattern of [EIP-2481](./eip-2481.md), with strictly increasing IDs so stale streamed responses need no unbounded tombstone set. Gaps are harmless. The eight messages belong to `lean`; envelope retrieval reuses ETH, including envelopes retained with validated wrappers outside the admitted pool.

A Merkle root supplied only by the announcer would not establish object validity or bound a malicious producer's total download cost. Since relay waits for full validation, a content hash and one source per assembly avoid a second commitment scheme and ambiguous blame for mixed corrupt chunks. The trade-off is restarting body retrieval when changing sources. Fixed 64 KiB offsets still allow bounded requests and same-source resume; a 32-chunk window grants at most 2 MiB and yields between messages.

Hash-only wrappers make envelope knowledge irrelevant to object identity and keep the worst-case object near the proof size, rather than the sum of thousands of full transactions. The 9 MiB ceiling accommodates the bounded wrapper from EIP-8288; it is not a recommended batch size. At most 18 MiB per source and 72 MiB globally may be buffered before validation, including recovery data and copies, regardless of peer or request count. Implementations may use lower limits and smaller batches.

Deriving profile IDs from locally configured keys avoids a separate verifier registry. Kind 2 supports bounded proof-only recovery, including fallback from broadcast. GetObjects resolves a known block hash to its descriptor; wrapper announcements already carry descriptors and need no extra lookup round trip. Authenticated IL proofs have an existing CL-to-EL path and need no duplicate unsigned EL package.

Validate-before-relay adds a full download and verification at each hop. Multi-megabyte wrappers cannot be assumed to propagate within the aggregation interval; small useful batches and measured latency matter more than filling the ceilings. The interval schedules aggregation and is not a network propagation guarantee.

Ethp2p isolates ordered retrieval control from independent response streams. Both bindings preserve the same object identities, validation rules and budgets, allowing a coordinated transport migration without requiring permanent RLPx support.

## Backwards Compatibility

Clients without this protocol continue using existing protocols. All participating nodes use the designated common binding; RLPx is not permanently required for proof transport. This EIP does not change RLPx, ETH encodings, block hashing, Engine API encodings or inclusion obligations. It extends ETH serving policy to envelopes retained with offered wrappers; a compatible negotiated ETH version is required for wrapper recovery.

Deployment depends on EIP-8288's canonical hash-only wrapper encoding, fixed verification profile, and proof-in-body block format. Kind 2 is optional and never a consensus prerequisite. The network's block-body and Engine API transports still need to carry the full EIP-8288 proof-size range.

Ethp2p-only operation requires the envelope-retrieval binding described above.

## Test Cases

[Commitment vectors](../assets/eip-8437/commitment-vectors.json) use a zero profile ID and `body[i] = i % 251`. [The executable checks](../assets/eip-8437/check_vectors.py) cover content hashes, object identities, chunk boundaries, message bounds and block-proof commitments. They test transport encodings, not EIP-8288 proof validity.

Implementations should also cover:

| Case | Expected result |
| --- | --- |
| Zero-length or oversized body; noncanonical RLP; excessive nesting or list count | Reject before large allocation |
| Same wrapper offered to peers with different envelope caches | Identical body and object ID |
| Requested block hash lacks a known header | Obtain the header before requesting chunks |
| Proof bytes differ from the header commitment, or dependencies differ from the block | Reject under EIP-8288 |
| Ordinary block acquisition already supplies a validated proof | No second required transfer |
| Request IDs have gaps; an ID repeats or decreases | Accept gaps; reject reuse or decrease |
| Unknown object with syntactically valid indices | Complete with Unavailable |
| Wrong live request type, object, index order or chunk length | Protocol violation |
| Duplicate chunk through another request to the same source | Consume credit, retain one copy, no renewed assembly progress |
| Chunk bytes conflict with an already retained index | Discard the source contribution |
| Complete says Served before all requested chunks arrive | Protocol violation |
| Cancel crosses the last Chunk and Served | Discard post-cancellation payloads; terminal response releases the slot |
| Objects arrives after cancellation | Check terminal structure and release slot without using results |
| Late response after expiry; requester and responder expire at different times | Discard retired responses; timing alone incurs no penalty |
| A body fails its content hash; another source offers the same descriptor | Discard partial bytes, retry within the original deadline and attempt bound |
| Source changes or reconnects; duplicate announcements or queue moves | No extended absolute lifetime or multiplied budgets |
| Requests across many peers would exceed the global byte ceiling | Refuse or defer before allocation |
| Complete body waits for verification or envelope recovery | Remains charged and expires normally |
| Envelope retained outside the admitted pool is requested through ETH | Serve it while offering its validated wrapper |
| Preliminary proof verifies but recovered envelopes do not validate the wrapper | No admission, reaggregation or relay |
| Envelope unavailable, local refusal, or transaction fails pool policy | No penalty solely for that reason |
| Profile is known but inappropriate for the target fork | No admission or timing-independent misbehavior inference |
| Proof parameters or enabled schemes change | Use the profile derived from the corresponding key |
| A signed IL carries a proof | Use CL gossip and Engine API, not a lean object |

Scheduling tests should cover bounded retry, completion-copy pressure, verification queues and control messages between chunk writes. Proof-verifier interoperability requires EIP-8288 profiles and test vectors.

### Ethp2p conformance

The Cancel frame for request 7 is `0700000002c107`; the retrieval control prefix is `10` and a response prefix for request 7 is `110000000000000007`. [The ethp2p framing checks](../assets/eip-8437/check_ethp2p.py) cover these encodings, fragmented reads, stream roles, payload ceilings and truncated frames. These checks do not establish QUIC/TLS or network interoperability. Implementations must additionally cover:

| Case | Expected result |
| --- | --- |
| ENR key differs from the authenticated TLS identity; invalid certificate; wrong ALPN; application 0-RTT | Reject the connection or prohibited early data before object processing |
| Certificate signature algorithm does not match its key type | Reject as an authentication failure, not an unhandled error |
| ClientHello carries no server name, `ethp2p` or another name | Ignore it; authenticate only by certificate |
| Ethp2p is the common binding but QUIC is unavailable or the bind fails | Fail to start or disable the protocol and report it; never continue on other bindings alone |
| Response streams for requests 2 and 1 arrive in that order | Accept independently; the control-stream requests themselves remain strictly increasing with gaps allowed |
| Wrong response ID, object ID or response type; two streams for one live request | Reject the contribution as a protocol violation |
| Partial prefix, oversized frame, extra bytes after a terminal response, or control-stream closure | Enforce bounds or terminate the binding as specified; retain chunks for same-source resume |
| FIN or reset before Complete; Cancel races Complete and FIN | Incomplete delivery or normal retirement, never premature Served or duplicate slot release |
| A known response stream resets after Cancel | Release the slot without waiting for a Complete message |
| Connection closes after some chunks; retrieval continues over RLPx | Same object ID and deadline; another source requires discarding partial body bytes |
| Same source sends a chunk over both bindings or opens more connections | One retained copy; shared per-node budgets and unchanged assembly progress for duplicates |
| Partial stream prefixes or repeated resets consume resources | Enforce pending-stream, cleanup and age limits without unbounded state |
| All chunks arrive but the object proof fails | Reject; no announcement or serving over either binding |
| Common binding changes at a coordinated activation | All participating nodes retain a common path; retrieval works without requiring RLPx fallback |

## Security Considerations

A content hash supplied by a malicious peer can match an invalid proof. Announcements and chunks therefore establish no validity, and full validation precedes relay. Finite per-peer and global byte, recovery and work budgets remain necessary against many peer identities; absolute deadlines bound withholding and slow streams.

Single-source assembly makes a mismatch attributable without blaming other peers, at the cost of restarting after a source change. Arithmetic on counts, offsets, lengths and credit must be checked before allocation, and proof decoders need their own resource bounds. Invalid proof checks can cost real work without corresponding sender effort.

RLPx chunking permits interleaving but does not remove TCP head-of-line blocking. QUIC isolates streams under shared congestion and resource limits. Neither binding reduces proving work, ensures availability or guarantees completion within a slot. Transport unavailability is not consensus invalidity.
