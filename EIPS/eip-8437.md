## Abstract

This EIP defines the `lean/1` devp2p capability and an optional ethp2p QUIC binding for discovering and retrieving [EIP-8288](./eip-8288.md) mempool wrappers, block proofs and inclusion-list packages. Receivers request 64 KiB chunks, check them against an object commitment, and resume retrieval across peers and transports. Objects require full validation before relay; chunk integrity alone does not establish proof validity. No consensus rules change.

## Motivation

Dependency witnesses and aggregated proofs can be much larger than ordinary transactions. Whole-object messages occupy the connection while being written and make interrupted retrieval expensive. Unsolicited objects also consume receiver resources before the receiver decides whether it needs them.

Requested chunks bound each transfer, allow selective recovery and let proof traffic interleave with other messages. A canonical commitment lets receivers combine chunks from different peers while checking that they belong to the same object.

Independent QUIC response streams also prevent packet loss on one transfer from blocking unrelated response streams. Sharing object commitments and validation across transports permits gradual deployment and fallback without rebuilding proofs or objects.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

EIP-8288 and the activated fork define proof and transaction validity, inclusion-list obligations, the mempool wrapper encoding and its limits. ### Encoding

Message data and object bodies use canonical RLP with exactly the field counts specified. Integers use the shortest unsigned encoding, with zero as the empty string; stated widths are range bounds, not fixed-width fields. Leading zeros, extra fields, trailing bytes, nonminimal length prefixes and wrong list/string types are invalid. Hashes are exactly 32 bytes. Byte strings sort lexicographically; tuples sort by their fields, comparing integers numerically. Lists MUST be checked against their count bounds before allocating elements; the outermost RLP list has depth one and nested transport lists MUST NOT exceed `MAX_RLP_DEPTH`. Transaction envelopes and proofs are opaque byte strings at this layer, parsed afterward by their own bounded parsers.

`H` is Keccak-256, not SHA3-256. It is distinct from EIP-8288's `DEPS_HASH`, which this EIP uses only through `get_deps_hash`. `RLP(x)` is canonical RLP. In commitment formulas, `U8`, `U32` and `U64` are fixed-width big-endian unsigned integers, `||` is byte concatenation, and a domain label is its ASCII bytes followed by one zero byte.

[RLPx](https://github.com/ethereum/devp2p/blob/76cf0a141e8aa8616e3305738d51101945387d3c/rlpx.md) compression, encryption, message-ID multiplexing and authentication are unchanged. Implementations MUST check the advertised uncompressed size before decompression and reject messages exceeding `MAX_MESSAGE_BYTES`. Body bytes travel only in requested Chunk messages, one chunk per message; there is no whole-object message, and implementations MUST NOT rely on RLPx frame fragmentation to carry an object.

### Capability and profiles

Peers negotiate capability name `lean`, version `1`, through the RLPx Hello exchange. All ten message IDs are reserved even if an optional object kind is unsupported or the capability is disabled after Status. Status MUST be sent without waiting for the peer's Status. A peer MUST NOT send any other message before accepting the peer's Status.

A **profile ID** identifies the verification key for an object's recursive STARK:

```text
profile_id = H("lean/1/profile\0" || AGGREGATED_VK)
```

`AGGREGATED_VK` uses the canonical byte encoding fixed by the activated EIP-8288 fork, never a client-specific key serialization. It fixes the cryptographic profile, including dependency hashing and encodings, verifier parameters and bounds, and the circuit's `enabled_schemes` and verification relations. Changing that scheme set requires a new key and therefore a new `profile_id`. Clients derive profile IDs from local fork configuration, never peer-supplied keys. A **common profile** appears in both Status messages and is supported locally.

A profile selects a verifier, not a fork or a valid chain. The receiver MUST check it against the applicable fork: the reconstructed header's fork for kind 2, the local target block for kind 1, and the authenticated inclusion-list context for kind 3. Forks sharing a key share the cryptographic profile and enabled schemes but may have different transaction or admission rules outside the circuit. Status MAY list known past and future profiles; activation does not update Status, and peers reconnect if new profiles must be advertised. A profile inappropriate for the receiver's target context is not by itself peer misbehavior.

The **STARK check** verifies `stark_proof` against `get_deps_hash(deps)` and the locally configured `AGGREGATED_VK` identified by `profile_id`. For kind-2 block proofs with no dependencies, `stark_proof` MUST be empty and no proof verification is performed, as EIP-8288's block validity rules require. Kind-3 proof fields are checked under EIP-8288's inclusion-list dependency proof rule. A kind-1 wrapper with empty `deps` uses mode 0, as EIP-8288 requires.

Status is sent exactly once in each direction:

```text
Status (0x00) = [1, chain_id, genesis_hash, profiles, kinds, max_object_bytes]
```

- The first field is the Status version, `1`.
- `chain_id` is an unsigned integer less than `2**256`.
- `genesis_hash` is 32 bytes.
- `profiles` is a nonempty, strictly ascending list of at most `MAX_PROFILES` 32-byte profile IDs.
- `kinds` is a bit mask in which bit `kind - 1` advertises support for that kind. Bit zero MUST be set and bits above two MUST be zero.
- `max_object_bytes` is an integer in `[1, MAX_OBJECT_BYTES]`: a local receive ceiling, not a promise to accept every smaller object.

The chain ID and genesis hash MUST match local configuration, and at least one profile MUST be common. An incompatible Status disables this capability; clients SHOULD keep other protocols on the connection. Malformed or repeated Status, or other messages received before Status, are protocol violations.

### Object kinds and canonical bodies

An **object** is a descriptor and its canonical body, whose length is in `[1, MAX_OBJECT_BYTES]`. A dependency is the EIP-8288 96-byte encoding `31 zero bytes || scheme byte || data_hash || verification_key_hash`; dependency lists use its `deduplicate_and_sort` order. `dependencies(tx)` follows EIP-8288 and is empty for transaction types without dependency frames. Only schemes enabled under EIP-8288 at the applicable fork are valid, as fixed by the fork's activated dependency profile (`enabled_schemes`); the profile and transactions must also satisfy the applicable fork's rules.

#### Kind 1: mempool wrapper

The context is the empty list. The body is the EIP-8288 wrapper encoding `RLP([transactions, mode, [deps, proof_content]])`, with `entry = [0, transaction_envelope] | [1, transaction_hash]`.

`transaction_envelope` is the exact [EIP-2718](./eip-2718.md) encoding, with a legacy transaction as its RLP, carried as an RLP byte string; its hash is `H(transaction_envelope)`. A hash entry carries exactly 32 bytes. The tag, not the length, distinguishes the two forms. `transactions` holds 1 to `MAX_TXS_PER_WRAPPER` entries in strictly ascending transaction-hash order. Replacing a full entry with a hash entry produces a different object.

Transactions MUST be [EIP-8141](./eip-8141.md) frame transactions. In both modes, `deps` MUST equal `deduplicate_and_sort` of the union of `dependencies(tx)` over all transactions, and each transaction MUST satisfy EIP-8288's `MAX_SIGS_PER_TX` and `MAX_STARKS_PER_TX` mempool limits across all frames. All dependency counts use deduplicated sets.

- Mode 0 carries one proof byte string per dependency, in `deps` order, verified with that dependency's scheme. It permits at most `MAX_LEANSIG_DEPS_PER_WRAPPER` signature and `MAX_LEANSTARK_DEPS_PER_WRAPPER` STARK dependencies.
- Mode 1 carries one `stark_proof`, which MUST pass the STARK check against `deps`, and permits at most `MAX_DEPS_PER_AGGREGATE` dependencies, of which at most `MAX_LEANSTARK_DEPS_PER_AGGREGATE` use `LEANSTARK_SCHEME`. Mode-0 witness-count limits do not apply.

No other mode is valid. Both modes remain bounded by `MAX_TXS_PER_WRAPPER`, `MAX_WRAPPER_BYTES`, `MAX_OBJECT_BYTES` and the activated verifier's proof-format and resource bounds. Counts and encoded lengths MUST be checked before large allocation or proof verification. A larger aggregate does not permit an individually inadmissible transaction.

After body integrity and encoding checks, receivers SHOULD verify witnesses or the aggregate proof against the claimed `deps` before fetching missing transactions. This preliminary check does not validate the wrapper: every hash entry MUST still be resolved and the exact dependency union checked before admission, reaggregation or relay. Recovery MUST stay within finite budgets even after a successful proof check, since the proof does not authenticate the transaction-hash list. Senders SHOULD announce a single entry form for a batch to all peers; per-peer hash-entry variants fragment availability across distinct object IDs. Senders retain recoverable envelopes while offering hash entries. For oversized envelopes this means retaining, under the same profile, a validated kind-1 object that is servable through `lookup_kind = 1` and contains the envelope as a full entry. Failed recovery leaves the wrapper unresolved, not invalid.

Nodes MAY maintain multiple wrappers covering bounded subsets of locally eligible transactions. EIP-8288's `AGGREGATION_INTERVAL` is a recommended scheduling cadence, not a proof deadline or a requirement to publish on every tick. Nodes SHOULD announce useful changes and schedule fairly between new transactions and maintained batches; they MAY forward validated wrappers without reaggregation. Replacing a batch MUST NOT invalidate older proofs or automatically cancel their transfers. Splitting or pruning a batch requires a matching proof for each resulting dependency set, with discards computed by EIP-8288's `discard_dependencies`.

#### Kind 2: block-proof sidecar

```text
context = [block_hash, block_number, transactions_root, block_deps_hash, skeleton_hash]
body = RLP([stark_proof])
```

`block_number` is a 64-bit unsigned integer; the other fields are 32-byte hashes. `stark_proof` is exactly the first element of the block's EIP-8288 `recursive_stark` header field. The one-element list keeps the body nonempty when `stark_proof` is empty.

An Objects response carries the descriptor with a **header skeleton**:

```text
skeleton = [proof_field_index, field_encodings]
skeleton_hash = H("lean/1/skeleton\0" || RLP(skeleton))
```

`field_encodings` lists 1 to `MAX_HEADER_FIELDS` byte strings, one per top-level field of the block's canonical header, in order. Each entry is the complete canonical RLP encoding of one field, including its prefix, except the entry at `proof_field_index`, which MUST be the empty byte string. `proof_field_index` is an unsigned integer less than the field count and MUST be the position of `recursive_stark` in that fork's header. The encoded skeleton is at most `MAX_HEADER_SKELETON_BYTES`.

Before requesting chunks, the receiver MUST check `skeleton_hash`, the placeholder, the context's block number and transactions root, and the remaining fields against the locally configured fork's header schema. Encoded fields use bounded parsing with maximum depth `MAX_RLP_DEPTH`. After retrieving the body, it replaces the placeholder with `RLP([stark_proof, block_deps_hash])`, concatenates all field encodings, and prefixes the RLP list header for that length; it MUST NOT re-encode entries as RLP strings. The reconstructed header hash MUST equal `block_hash`. The skeleton itself is not a header and MUST NOT be stored or used as one.

Before a sidecar is used as a block proof, the receiver MUST obtain the block body through the existing block protocol and check that its transactions root matches the header, that `dependencies_fit_block(dependencies(block))` holds, that `block_deps_hash == get_deps_hash(dependencies(block))`, and that `stark_proof` passes the STARK check against `dependencies(block)`. A header whose hash matches a peer-requested `block_hash` does not establish canonical-chain membership.

This kind transfers the proof already committed by the header in bounded messages. It does not change header contents or hashing, ETH header responses or block-body availability, and does not permit processing a block without its proof.

#### Kind 3: inclusion-list package

The context is `[package_hash]`, where `package_hash = H(body)`. The body is the EIP-8288 FOCIL `[transactions, recursive_stark]`:

```text
RLP([transactions, [stark_proof, deps_hash]])
transactions = [transaction_envelope, ...]
```

`transactions` holds at most `MAX_TXS_PER_PACKAGE` full envelopes, encoded as in kind 1, in inclusion-list order; the transport neither sorts them nor replaces them with hashes. Let `dependencies(transactions)` be `deduplicate_and_sort` of the union of `dependencies(tx)` over `transactions`. Kind-3 proof fields are checked under EIP-8288's inclusion-list dependency proof rule against `dependencies(transactions)`. A package whose proof fields fail that rule is invalid for transport. This does not erase an independently authenticated inclusion list: EIP-8288 defines which entries still impose inclusion obligations under [EIP-7805](./eip-7805.md).

This kind carries no signature, author or slot. Before applying inclusion obligations, a receiver MUST associate the package with an authenticated inclusion list from the existing consensus-layer protocol, matching its ordered transactions and any proof commitment required by the fork. `package_hash` is a transport lookup key, not the consensus-layer inclusion-list root. An unassociated package establishes no inclusion obligation.

### Descriptors and identity

```text
descriptor = [kind, profile_id, context, byte_length, content_hash, chunk_root]
content_hash = H(body)
context_hash = H("lean/1/context\0" || RLP(context))
object_id = H("lean/1/object\0" || RLP(descriptor))
```

`kind` is 1, 2 or 3 and `context` has that kind's form. `byte_length` is a 64-bit unsigned integer within the object bounds. An encoded descriptor is at most 512 bytes. Before requesting chunks, a receiver MUST check its encoding, context and geometry; for kind 3, `context[0]` MUST equal `content_hash`.

An **assembly** is a receiver's partial copy of an object. Clients key objects and assemblies by `object_id` and transfers by `(connection, request_id)`. Announcing a known descriptor MUST NOT create another assembly, and claims from different peers merge only when their descriptors are identical.

### Chunk commitments

The body is split at fixed `CHUNK_BYTES` offsets without padding:

```text
N = ceil(byte_length / CHUNK_BYTES)
W = smallest power of two >= N
depth = log2(W)
S = U8(kind) || profile_id || context_hash || content_hash || U64(byte_length) || U32(N)
chunk[i] = body[i * CHUNK_BYTES : min((i + 1) * CHUNK_BYTES, byte_length)]
```

Thus `1 <= N <= 1024` and `0 <= depth <= 10`. Every chunk except the last is exactly `CHUNK_BYTES`; the last is `byte_length - (N - 1) * CHUNK_BYTES` bytes. `N`, these lengths and `depth` are the object's **geometry**.

The commitment is a perfect binary tree of `W` leaves:

```text
leaf[i] = H("lean/1/leaf\0" || S || U32(i) || U32(len(chunk[i])) || chunk[i])  for i < N
leaf[i] = H("lean/1/empty\0" || S || U32(i))                               for N <= i < W
parent = H("lean/1/node\0" || U8(level) || left || right)
chunk_root = H("lean/1/root\0" || S || tree_root)
```

`level` is zero for parents of leaves and increases toward the root. For `W == 1`, `tree_root` is the single leaf.

A **branch** lists exactly `depth` sibling hashes from the leaf level upward. At each `level`, bit `level` of `index` selects the order: zero hashes `(current, sibling)`, one hashes `(sibling, current)`. The result, under the root domain, MUST equal the descriptor's `chunk_root`, and `index` MUST be less than `N`. A sibling covering only padding leaves MUST equal the canonical empty subtree. After reconstruction the receiver MUST recompute the full canonical root and `content_hash`.

### Messages and request lifecycle

IDs are relative to the capability's negotiated message offset:

| ID | Message | Direction |
| --- | --- | --- |
| `0x00` | Status | Both |
| `0x01` | AnnounceObjects | Both |
| `0x02` | GetObjects | Request |
| `0x03` | Objects | Response |
| `0x04` | GetChunks | Request |
| `0x05` | Chunk | Response |
| `0x06` | Complete | Terminal GetChunks response |
| `0x07` | Cancel | Requester to responder |
| `0x08` | GetTransactions | Request |
| `0x09` | Transactions | Response |

Request IDs are 64-bit unsigned integers. On each connection a peer numbers its requests of all three types consecutively from one, never wrapping or reusing an ID; each direction has its own sequence, and responses echo the request's ID. A new incoming request whose ID is not one more than the previous incoming ID (or one, for the first) is a protocol violation, even if refused. Each endpoint MUST keep at most `MAX_REQUESTS_PER_PEER` locally live requests per direction. Responders return Busy for requests they cannot accept. Receiving a request while at the local limit MUST NOT by itself incur a penalty, since expiry times can differ.

Each endpoint measures deadlines with its own monotonic clock: the requester starts when sending the request, the responder when receiving it. Request idle time resets only when receiving a valid first response for a requested result, or when writing that result on the responder. A chunk already obtained from another peer can therefore advance a request without advancing the assembly. Each endpoint retires the request at its idle or absolute deadline, whichever comes first; no synchronized expiry is assumed. Disconnection releases request state. Neither requests nor cancellation reset an assembly's absolute age.

#### AnnounceObjects (0x01)

```text
[descriptor, ...]
```

The list holds 1 to `MAX_ANNOUNCEMENTS` descriptors in strictly ascending `object_id` order. A sender MUST announce only objects it holds in full and has validated as specified for their kind, including, for kind 2, the block itself. Announced objects MUST use a common profile and a kind supported by both peers, and fit the receiver's advertised ceiling. Receivers MAY ignore other descriptors without allocating assemblies.

Announcements neither require receiver action nor establish validity. Repetition earns no credit or retention. Peers SHOULD suppress unchanged announcements and rotate bounded selections fairly across useful objects.

#### GetObjects (0x02) and Objects (0x03)

```text
GetObjects = [request_id, selectors]
selector = [kind, profile_id, lookup_kind, lookup_key]
Objects = [request_id, results]
result = [status, descriptor_or_empty, auxiliary]
```

`selectors` holds 1 to `MAX_LOOKUPS` distinct entries in strictly ascending `(kind, profile_id, lookup_kind, lookup_key)` order. `lookup_key` is 32 bytes. `lookup_kind = 0` looks up the primary identity: the object ID for kind 1, the block hash for kind 2, or the package hash for kind 3. `lookup_kind = 1` is valid only for kind 1 and looks up a transaction hash whose full envelope is wanted. No other lookup kind is valid.

For a transaction-hash lookup, the server returns a validated kind-1 object under that profile containing the transaction as a full entry; it need not build one. The receiver checks descriptor fields immediately and the requested entry after body reconstruction. Once body integrity and encoding checks pass, it MAY extract the full envelope and check its hash without resolving other hash entries or verifying that wrapper's proofs. This does not admit or authorize relay of either wrapper. Clients MUST NOT chain hash recoveries. This lookup supports envelopes too large for a Transactions message.

Results correspond one-for-one to selectors. Statuses are `0 = OK`, `1 = Unavailable` (unknown or no longer retained), `2 = Busy` (local resource pressure; no later response is promised), `3 = Unsupported` (profile not common or kind not implemented), and `4 = TooLarge` (exceeds the requester's `max_object_bytes`). A non-OK result has empty byte strings in both remaining fields. For OK, `descriptor_or_empty` is a descriptor matching the selector and within the requester's ceiling, and `auxiliary` is the skeleton for kind 2 and empty otherwise. Receivers MUST check descriptors and skeletons before retaining them. Announcements do not carry skeletons, so a receiver obtains a kind-2 skeleton through GetObjects before requesting chunks, unless it already has it.

The uncompressed Objects message is at most `MAX_METADATA_RESPONSE_BYTES`. OK results that would exceed it are returned as Busy; the responder MUST NOT omit or split results. The response is terminal. A request never obliges a peer to prove, fetch from other peers, retain history, or allocate an object it does not hold.

#### GetChunks (0x04), Chunk (0x05), and Complete (0x06)

```text
GetChunks = [request_id, object_id, indices]
Chunk = [request_id, object_id, index, chunk_bytes, branch]
Complete = [request_id, object_id, status]
```

The requester MUST already hold a well-formed descriptor using a common profile and a kind supported by both peers, within its receive ceiling. `indices` is a strictly ascending list of 1 to `MAX_CHUNKS_PER_REQUEST` 32-bit integers less than `N`. The request grants **credit** for exactly those chunks, at most 2 MiB of body data. A responder without the descriptor checks only the wire bounds (including indices below 1024) and returns Unavailable; it cannot check unknown geometry. A responder with the descriptor MUST check its profile, kind and size before serving.

The responder sends at most one Chunk per requested index, in request order, and nothing unrequested. It MAY stop early for unavailability or resource pressure but MUST then send Complete. Complete statuses are `0 = Served`, `1 = Unavailable`, `2 = Busy`, `3 = Unsupported`, `4 = Cancelled` and `5 = TooLarge`. Served means every requested chunk was written; it does not mean the receiver accepted anything. Complete is terminal and releases unused credit, and a request never expands to further indices.

A Chunk must match the outstanding request's object ID, next expected index, chunk length and branch depth. The receiver MUST verify its branch before retaining its bytes. It tracks received indices separately from retained chunks: an identical chunk obtained through another request consumes this request's credit but MUST NOT allocate another copy or refresh the assembly's idle timer. Repeating an index within one request is a protocol violation. Complete must match the request's object ID; Served before every requested Chunk has arrived is a protocol violation. Locally discarded chunks MAY be requested again.

#### Cancel (0x07)

```text
[request_id]
```

Cancel names a request originated by its sender. The responder stops scheduling chunks and sends Complete with Cancelled for a live GetChunks request; a Chunk already being written MAY finish first. A terminal response already being written MAY finish without replacement. For GetObjects or GetTransactions not yet being answered, the responder sends the normal terminal response with Busy for every result. Cancels for unknown or completed requests are ignored.

The requester marks a cancelled request but retains its slot until a terminal response or local expiry. It MUST discard all subsequent response payloads for that request without proof verification, body hashing, retention or further recovery. A structurally valid terminal response of the expected type, with the matching object ID where present, releases the slot, including Served crossing Cancel. Responses to retired IDs are discarded; ID zero or above the highest issued ID is invalid. The highest issued ID and bounded live-request map suffice. Framing, structure, count, size and rate bounds still apply. A wrong response type for a live request is a protocol violation. Cancellation does not invalidate previously retained chunks.

#### GetTransactions (0x08) and Transactions (0x09)

```text
GetTransactions = [request_id, transaction_hashes]
Transactions = [request_id, results]
result = [status, transaction_envelope_or_empty]
```

`transaction_hashes` is a strictly ascending list of 1 to `MAX_TXS_PER_REQUEST` hashes, each referenced by a retained wrapper being resolved. Clients MUST bound concurrent unresolved wrappers and requested hashes, and MUST NOT request hashes from any other source.

Results correspond one-for-one to the hashes. Statuses are `0 = OK`, `1 = Unavailable`, `2 = Busy` and `4 = TooLarge`; Unsupported does not apply because this request has no profile or kind, and a result with status 3 is malformed. An OK value is a canonical envelope whose hash equals the requested hash; other statuses carry the empty byte string. The uncompressed Transactions message is at most `MAX_TX_RESPONSE_BYTES`: the responder returns Busy for entries that would exceed it and TooLarge for an envelope that cannot fit even with all other results empty. Responses MAY use envelopes retained with validated wrappers even if absent from the transaction pool; they MUST NOT trigger historical searches or peer fetches. A requester MAY use negotiated ETH transaction retrieval instead, extracting and hash-checking the canonical envelope from that protocol's representation.

Once all hash entries are resolved, the receiver validates the wrapper as kind 1 and applies normal transaction admission. Pool rejection, nonce changes and fee policy are not protocol violations, and an unavailable entry is not evidence of misbehavior.

### Reassembly, resume, and multiple peers

Clients MUST keep at most one assembly per object ID, indexing verified chunks by index. Requests and peers can interleave; ordering is required only within each request. Resume requests only missing indices. Announcements do not attribute existing chunks to the announcer.

Before allocating or copying a chunk, a client MUST charge its bytes, branch, bookkeeping and pending verification work to finite per-peer and global budgets; a declared length MUST NOT trigger allocation of that length. Completed objects MAY be streamed into a bounded store; a completion copy MUST be reserved before copying and stay charged through validation and admission.

Assembly timers start when an assembly is created for retrieval, not on an announcement or its first chunk. Assemblies expire at their idle or absolute deadline independently of incoming messages. Idle time resets on a newly verified missing chunk or a newly resolved missing transaction. During direct transaction recovery, a new verified chunk of the recovery object also advances the waiting wrapper's idle timer; starting another recovery or receiving duplicates does not. Recovery objects have their own bounded assemblies, and nothing extends any assembly's original absolute deadline. Expiry releases its bytes and metadata and cancels work no longer needed by a live assembly. Completed objects awaiting validation or recovery remain subject to these deadlines and budgets; queue moves MUST NOT reset them.

Receivers SHOULD spread disjoint missing indices across useful peers, limiting duplicate requests and outstanding credit, and MAY retry stalled indices on another peer within the assembly's lifetime. Invalid data from one source MUST NOT cause valid chunks from other sources to be discarded, and a disconnected or unavailable peer does not invalidate the object. Source lists, announcement and duplicate caches, and retry schedules MUST be bounded, including under many peer identities. Peers MAY evict data and later answer Unavailable or Busy; completion is not guaranteed under withholding or insufficient capacity.

### Validation and relay

With all chunks present, the receiver MUST check the length, `content_hash`, canonical `chunk_root` and canonical body encoding, then apply the kind's validation. Sender-supplied metadata MUST NOT substitute for these checks.

A branch authenticates a chunk only to the descriptor's `chunk_root`, which is untrusted: neither a known block hash, a matching content hash nor RLPx peer authentication authenticates it. This EIP defines no producer signature or consensus commitment to `chunk_root`, so a client MUST NOT announce, serve, admit or reaggregate any part of an object until it has reconstructed and fully validated it.

After full wrapper validation, admission is evaluated per transaction. Rejection for current state, fees or local pool policy MUST NOT invalidate the wrapper's proof or force rejection of its other transactions. A validated wrapper MAY be retained as a proof object without presenting its transactions as admitted. EIP-8288 requires the proof format to support every dependency set within its limits; a receiver whose local verifier cannot verify an object within them refuses it locally and MUST NOT treat it as invalid. Relaying a changed subset still requires a proof matching its exact dependency union. No Complete status acknowledges admission or retention.

### Scheduling and errors

Senders MUST apply backpressure before serializing chunks, MUST yield between Chunk messages so that queued messages of other protocols are serviced at the next message boundary, and MUST NOT queue a whole object as serialized messages. Implementations SHOULD use small write windows and schedule fairly across objects, peers and capabilities.

Malformed encodings, bad branches, inconsistent geometry, mismatched transaction hashes, unrequested data and invalid proofs are invalid peer data: the client MUST discard the contribution and stop the associated transfer, and MAY disable `lean/1` for, disconnect or penalize the peer. Size violations MUST be rejected before large allocation or decompression. Unknown message IDs are protocol violations. Incompatibility, Unavailable, Busy, TooLarge, local queue exhaustion, cancellation, expiry and pool rejection of a validly proven transaction MUST NOT by themselves be treated as misbehavior.

Verification, transaction-admission and proving queues MUST have finite concurrency and backlog, and Busy results MUST NOT create unbounded retries. Clients SHOULD throttle sources that repeatedly send invalid data or consume credit without useful progress, while tolerating isolated stalls.

### Optional ethp2p binding

Clients implementing `lean/1` MAY additionally use the [ethp2p transport architecture](https://github.com/ethp2p/ethp2p/blob/3a475961022f667778ce1c2af685388f694689ef/specs/001-ethp2p.md) with the binding below. It defines its own application negotiation and framing over authenticated QUIC; it does not use the ethp2p broadcast framework's channels or coding strategies. All object encodings, commitments, validation, request credit and deadlines above apply except where this section explicitly changes stream handling. RLPx support remains required.

#### Discovery and authentication

An [EIP-778](./eip-778.md) v4 node record MAY advertise `leanq = [1, udp_port]`, an RLP list whose first integer is this binding's version and whose port is in `[1, 65535]`. The endpoint uses the record's `ip` or `ip6` address and the advertised port. Unknown versions are ignored. Dialers MUST verify the record's signature and MUST NOT infer support from a discovery UDP port alone.

The binding uses QUIC version 1 ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)) and TLS 1.3 with the ALPN identifier `ethp2p_lean_1`. Both peers MUST authenticate using the [libp2p TLS peer-authentication rules](https://github.com/libp2p/specs/blob/f201689524a23af835119834d7db75bbc71c3549/tls/tls.md#peer-authentication), with a secp256k1 identity key. The dialer MUST match that key to the signed node record's key; the certificate's separate signing key is not the node identity. The authenticated identity is also the peer's RLPx node identity for resource accounting. This ALPN replaces the libp2p ALPN; there is no additional protocol or stream-multiplexer negotiation. Application data MUST NOT use 0-RTT and MUST NOT be processed before peer authentication completes.

Failure to negotiate this binding permits bounded retry or RLPx fallback and does not imply invalid objects. A node MAY use both transports, but MUST account for requests, buffered bytes and verification work jointly per authenticated node key and globally. Separate connections do not grant separate per-peer budgets.

#### Streams and framing

Each endpoint opens exactly one outbound unidirectional **control stream**, starting with byte `0x00`, then Status as its first frame. It sends Status without waiting for the peer. The existing Status compatibility checks and once-per-direction rule apply; the peer's Status MUST be accepted within `MAX_REQUEST_IDLE_SECONDS` after authentication. Subsequent control frames may contain only AnnounceObjects, GetObjects, GetChunks, Cancel or GetTransactions. Thus requests retain their consecutive IDs and arrival order. Request IDs are scoped to a connection and direction; a response from another connection cannot satisfy a request.

Every response uses one new unidirectional **response stream**, starting with byte `0x01 || U64(request_id)`. It carries only the response sequence for that live request: Objects; Transactions; or zero or more Chunk frames followed by Complete. IDs within every frame MUST match the stream prefix, and Chunk and Complete MUST match the requested object. Chunks retain their per-request ordering. Response streams for different requests may arrive and advance in any order.

Each frame is:

```text
U8(message_id) || U32(payload_length) || RLP(message_data)
```

`payload_length` counts only the RLP bytes and MUST be in `[1, MAX_MESSAGE_BYTES]`; the tighter Objects and Transactions ceilings still apply. Receivers MUST check the ID, stream role and length before allocating or reading the payload into memory. Payloads retain canonical RLP and nesting rules. This binding uses no Snappy or other application compression, QUIC datagrams or bidirectional streams. Unknown stream types and message IDs are protocol violations.

A live request has at most one response stream. The responder MUST finish that stream with FIN immediately after its terminal response; the requester retires the request on receipt of that response and FIN. Extra bytes after a terminal response are invalid. FIN before a terminal response or a stream reset is incomplete delivery, never Served; retained valid chunks remain usable. A response prefix for a retired request is discarded without payload work; zero or an ID above the highest issued ID is invalid. A duplicate response stream for a live request is a protocol violation.

The control stream MUST remain open for the connection's lifetime. Its closure, reset, incompatible Status or protocol violation terminates this binding and releases its requests. Previously verified chunks MAY be resumed elsewhere within their existing assembly deadlines.

#### Cancellation and resource bounds

Cancel retains its existing meaning on the control stream, including the responder's terminal response. Sending Cancel alone does not release the request slot: a terminal response and FIN, a received reset, or local expiry does. A reset does not acknowledge admission or invalidate previously retained chunks.

At request expiry, clients retire its ID, stop associated work and cancel any response stream using QUIC `STOP_SENDING` or `RESET_STREAM`, as appropriate, with application error `0x01`. Cleanup remains charged until resources are released. An unopened or unidentified response cannot keep the request alive. Resets, stream creation, retries and switching transport MUST NOT refresh request or assembly deadlines. Known requests refused before sending a response use their normal Busy, Unsupported or TooLarge result; stream pressure alone is not peer misconduct. If no response stream is available, a refusal MAY wait in a bounded queue until capacity is available or the request expires; it MUST NOT exceed stream or queue limits to report Busy.

Clients MUST bound connections, pending streams, partial prefixes, transport receive buffers and reset-cleanup state before parsing application messages. Each connection has one control stream per direction; at most `MAX_REQUESTS_PER_PEER` response streams may be live per authenticated peer in each direction across connections. Unidentified streams count against the response allowance. New stream allowances MUST be replenished only as bounded state is released; QUIC flow-control and stream-count limits MUST enforce the receiver's budgets.

An incomplete stream prefix expires within `MAX_REQUEST_IDLE_SECONDS` of stream acceptance. Once identified, a response stream uses its request's original deadlines. An incomplete control frame expires within `MAX_REQUEST_IDLE_SECONDS` of its first byte; this does not expire an otherwise idle control stream. Trickle bytes alone MUST NOT refresh these parsing deadlines.

Implementations MUST reserve receive and send capacity for the control stream, apply backpressure before serializing responses, and schedule fairly between response streams and other traffic. QUIC streams share connection bandwidth and congestion control; stream isolation does not replace byte or work budgets.

#### Reassembly and relay

RLPx and QUIC contribute to the same assembly indexed by `object_id`, with one copy of each verified chunk and one original absolute deadline. Credit and response ordering are tracked separately for each request. Duplicate bytes consume that request's credit without refreshing assembly progress. Closing one connection MUST NOT discard valid contributions from others.

Only fully validated objects may be announced or served over either transport. Peer authentication, a successful QUIC transfer and a valid chunk branch do not authenticate the object's proof. This binding adds no producer commitment, erasure coding or permission to relay before full validation.

## Rationale

Fixed chunks and domain-separated hashes give exactly one tree per descriptor. A 64 KiB chunk needs at most ten sibling hashes (320 bytes), below 0.5% of a full chunk before message framing. The 32-chunk request window amortizes round trips over up to 2 MiB while allowing scheduling between messages. These bounds are transport choices, not measured optimal values or proof-size limits.

Announcement followed by requested retrieval follows [EIP-2464](./eip-2464.md); size-aware selection follows [EIP-5793](./eip-5793.md). Request IDs follow the correlation pattern of [EIP-2481](./eip-2481.md), but are deliberately consecutive and never reused here, so stale streamed responses can be rejected without unbounded tombstones. These rules belong to the separate `lean` capability and do not change ETH messages.

Deriving profile IDs from locally configured keys avoids a separate verifier registry; changing a key changes its ID without letting peers introduce keys.

[EIP-8411](./eip-8411.md) authenticates its chunk root through a signed builder bid. Proof objects here have no such commitment, so branch verification provides integrity and multi-source retrieval, while relay waits for full validation.

Mode 0 bounds individual witness checks; mode 1 replaces those checks with one aggregate verification but still requires processing its dependency and transaction lists. Separate aggregate bounds permit useful merging without unbounded metadata or admission work. The ceilings are not target batch sizes or measured proving capacity. Independent batches avoid rebuilding an entire pool on a timer, while retained constituent proofs can make later splitting cheaper. These limits are EIP-8288's; this EIP only transfers objects within them.

Kind-2 sidecars carry proof bytes the header already commits to; the skeleton lets a client rebuild the canonical header from bounded messages. Removing the proof from the header would be a separate Core change.

Kind 3 carries the EIP-8288 FOCIL package, preserving transaction order and deriving the proof statement from those transactions.

The ethp2p binding keeps small control messages ordered and gives each response an independent stream. This preserves request correlation and cancellation while isolating response delivery from packet-loss stalls in unrelated streams. The same identities and budgets prevent a second transport from multiplying a peer's resource allowance. Erasure-coded broadcast would require a separate coding commitment and relay policy; it is not needed for this transport binding.

## Backwards Compatibility

Clients without `lean/1` continue using their existing protocols. Clients without the optional ethp2p binding can still exchange the same objects over RLPx. This EIP does not change RLPx, the ETH protocol, transaction or block validity, block hashing, Engine API encodings or inclusion-list obligations, and transport availability is not a consensus prerequisite.

Deployment requires the activated EIP-8288 fork to fix the verification key and its byte encoding, dependency hash function, proof encoding and header schema. This EIP does not fill in those Core parameters. In particular, a large proof still occupies the canonical header; kind 2 does not make oversized ETH header responses possible.

### Ethp2p conformance

The Cancel frame for request 7 is `0700000002c107`; the control-stream prefix is `00` and a response-stream prefix for request 7 is `010000000000000007`. [The ethp2p framing checks](../assets/eip-8437/check_ethp2p.py) cover these encodings, fragmented reads, stream roles, payload ceilings and truncated frames. Implementations must additionally cover:

| Case | Expected result |
| --- | --- |
| ENR key differs from the authenticated TLS identity; invalid certificate; wrong ALPN; application 0-RTT | Reject the connection or prohibited early data before object processing |
| Response streams for requests 2 and 1 arrive in that order | Accept independently; the control-stream requests themselves remain consecutive |
| Wrong response ID, object ID or response type; two streams for one live request | Reject the contribution as a protocol violation |
| Partial prefix, oversized frame, extra bytes after a terminal response, or control-stream closure | Enforce bounds or terminate the binding as specified; retain valid chunks |
| FIN or reset before Complete; Cancel races Complete and FIN | Incomplete delivery or normal retirement, never premature Served or duplicate slot release |
| A known response stream resets after Cancel | Release the slot without waiting for a Complete message |
| Connection closes after some chunks; retrieval continues over RLPx | Same object ID and assembly deadline; request IDs remain connection-local |
| Same chunk arrives over both bindings, or the same node opens more connections | One retained copy; shared per-node budgets and unchanged assembly progress for duplicates |
| Partial stream prefixes or repeated resets consume resources | Enforce pending-stream, cleanup and age limits without unbounded state |
| All chunks arrive but the object proof fails | Reject; no announcement or serving over either binding |

## Security Considerations

Well-formed chunks can still carry invalid proofs or never-completing objects. Per-peer and global budgets, including verification queues, must account for many peer identities. Absolute deadlines prevent slow streams, unresolved transactions and queue moves from retaining resources indefinitely.

Chunk roots have no producer authentication, so early relay would amplify spam. Full content-hash, canonical-root and proof checks are required before relay. Arithmetic on counts, offsets, lengths and credit must be checked before allocation; proof decoders require their own work and allocation bounds.

Chunking lets RLPx messages interleave but does not remove TCP head-of-line blocking. The optional QUIC binding isolates delivery between response streams, subject to shared congestion and resource limits. Neither binding reduces proving work, ensures block availability or guarantees completion within a slot. An unavailable sidecar or an unsupported profile is not a consensus-invalidity condition.
